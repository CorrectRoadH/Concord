# 按 Spec 验收

对照 Spec 检查一组改动。只读，不修改文件。

1. 确定范围：要验收的 diff（提交区间或未提交的改动）与它声称满足的 Feature、Use Case 或步骤。
2. 运行 `concord check` 与 `concord trace gaps`；用 `concord review` 生成改动涉及的 Spec、代码与测试材料。
3. 逐条对照：每个步骤的行为、输出字段、错误码与退出码是否和 Spec 一致；按声明的前置条件与失败判据，在隔离环境通过真实入口复现关键行为，同时观察副作用。不依据实现者的自述或测试名称判断；结束后回收本次创建的资源并保留证据。
4. 检查代码是否符合项目的代码规范（本仓库见 `docs/engineering/code/README.md`）与架构文档的分层和依赖规则。
5. 检查过程是否守规则：Spec 是否先于实现修改；实现是否自行决定了 Spec 没写的公共语义；`docs/` 是否混入过程记录。

## 涉及形式验证时

检查性质是否对应 Spec，假设、探索边界、未覆盖项是否明确。核对模型与当前代码的原子步骤、分支、取值范围和共享状态写入路径；验证仍能运行和通过，不代表模型仍描述当前代码。

审阅验证能检出所声明故障的证据，区分模型故障注入与真实代码故障注入。反例按领域事件序列逐步对照代码，在可行时复现；步骤无法发生时先检查模型。审阅保持只读，不修改产品、模型或性质来取得通过结果。

结论逐条写：位置、Spec 依据、实际观察、需要怎样改。分别报告 Spec 缺失或冲突、验证工具失效、模型偏离、产品缺陷与环境阻塞，行为保证的变化交回 Spec。说明实际验证范围、未运行或中止的检查、证据位置和未回收资源；标记不表示覆盖，模型通过仅限声明的假设与边界。
