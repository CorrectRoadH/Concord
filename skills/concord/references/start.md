# 开始写 Spec

结合用户这次想完成的事和仓库现状，写出能阅读、能指导实现的 Spec。已有明确目标时直接推进；源码存在与否只是线索，不替用户决定写作方向。

先读项目说明、相关旧文档、品味与术语，按需查看入口和测试。选择适用的指南，可以组合使用：

| 本次目标 | 指南 |
| --- | --- |
| 整理已有能力 | `concord --skill docs-from-code` |
| 从目标建立新项目的 Spec | `concord --skill docs-from-scratch` |
| 新增或修改能力 | `concord --skill spec` |

只收到“刚初始化，开始写”而目标不清楚时，根据看到的产品给出具体建议，例如：“我建议先整理打开书籍并继续阅读的路径；这次还有要一起设计的新需求吗？”不要固定询问从零写还是补写，也不要重复确认用户已明确的范围。未决目标不写成既定规则，不依赖回答的工作继续。

运行 `concord --skill document`，先看随正文输出的 docs 目录树，再读完整 Feature 与 Use Case 示例。它们来自 Concord 随包文档，展示组织方式和成稿，不是当前项目的需求；无需在当前项目查找示例文件或复制整棵树。

按本次范围先写一份代表性 README 与一条用户路径，检查主要使用者能否照着使用、步骤是否推进同一个目标，再扩写。用户追加需求时纳入当前范围，只调查它依赖的现状，不等待整仓补写或测试标记完成。

写 Spec 的请求不自动授权实现。仅文档任务直接编辑 docs；代码与测试关联在正文稳定且任务包含接入时进行。交付前运行 `concord check`，报告范围、未决问题与未验证结果；检查不能代替正文审阅。
