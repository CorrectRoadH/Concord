# Spec 与文档

已采用的当前目标写入 Feature，叶子用户路径写入 Use Case；设计未完成或暂不实现的方向写入 Roadmap（与 Feature 同体裁），还没定下来的取舍写入 Design，开发本仓库所需的维护能力（构建、测试、性能测量等）写入 Engineering。

Spec 正文采用声明式表达：写产品必须具备的行为、边界与验收，不写“这轮做了什么”、开发流水账、实施进度或临时计划。用户操作流程、状态迁移和验收步骤可以保留。排障经过与交付经验写进 `memory/`；待调查观察写进 `docs/issues/`。

## 布局与创建

Feature 目录包含 README（必需）与按需选用的固定页面种类，文件名就是种类；Engineering 与 Roadmap 使用同一组种类，完整职责见随包 `docs/document-model.md` 的「页面种类」。

- `use-case/<u>.md` 是一个用户旅程，`use-case/README.md` 是可选的导航页；Use Case 不嵌套，也不跨文件。
- 除 README、`use-case/`、`performance.md`、`concepts.md` 与 `writing.md` 外，一种页面写不下时，把 `<种类>.md` 换成 `<种类>/` 目录：入口是 `<种类>/README.md`，其余页面自由命名，种类与目录相同。单页与目录不能并存。
- 文档包内无法归类的页面由 `check` 报告 `UnknownPageKind`，页面照常可读可编辑；按内容把它拆到对应种类，不靠改名凑合。项目的说明性文档放在包外，例如 `docs/guides/<g>.md`。
Spec、Roadmap 与 Design 没有 frontmatter：身份是仓库相对路径，名称是正文唯一的一级标题（代码块中的标题不计），Use Case 属于所在目录的 Feature。

直接创建目录与文件即可。`concord new` 按随包模板创建，页面在创建时选择，README 必需，其余可选：

```sh
concord new feature login --pages cli,use-case
concord new use-case expired-token
concord new design session-store
```

`--pages` 可选 `use-case`、`cli`、`library`、`api`、`format`、`ui`、`performance`、`architecture`、`data-model`，用于 Feature、Engineering 与 Roadmap；`concepts.md` 与 `writing.md` 直接编辑。其它参数以 `concord new --help` 为准。名称允许 Unicode 字母、组合标记和数字，可用单连字符分隔，保留原样，不翻译或自动更改大小写；禁止路径分隔符、空白和路径穿越。用 `concord list [类别]` 发现文档，用 `concord show <路径或选择器>` 读取文档及其关系、测试与实现；短选择器在同类中有歧义时具名拒绝，改写完整路径。

## 写作指南

先问读者要回答什么，再决定写在哪一页：

| 读者的问题 | 写在 | 写法 |
| --- | --- | --- |
| 功能对使用者做什么 | Feature README | 产品功能：谁用它、能做什么、上手示例、怎样工作（配图解）、Use Case 导航 |
| 某个情形下会发生什么 | Use Case | 一个情形一个 Use Case：用户目标、起始状态、带 `{#id}` 的逐步动作与输出、结果、Spec 来源 |
| 命令怎样调用 | cli | argv、人读输出、stdout 与 stderr、`--json` 字段、退出码、具名错误、最小示例 |
| 库怎样调用 | library | 导出的签名、返回值、失败 |
| 其它程序通过网络协议怎样调用 | api | HTTP 路由、RPC 方法与事件，请求与响应、状态码、错误、兼容规则 |
| 使用者编辑或读取的文件长什么样 | format | 受支持文件的路径、语法、字段、校验错误与示例 |
| 界面怎样呈现和响应 | ui | 布局、交互状态、键盘与可访问性、视觉验收 |
| 多快才算合格 | performance | 场景 ID、测量内容、预算与理解预算所需的前提 |
| 它是怎么实现的 | architecture | 模块与职责、数据流、不变量、失败阶段、资源生命周期、依赖选型 |
| 内部存什么 | data-model | 实体、存储结构、字段约束、索引、事务边界、数据生命周期 |
| 还没定下来的取舍 | Design | 要决定什么、几种做法和各自的代价；定下后写进 Spec 并删除 |
| 排障经过、根因、经验 | Memory | `memory/<id>.md` |
| 缺陷、请求与待调查的观察 | Issue | `docs/issues/<id>.md` |

行为页的规范性陈述要能被测试断言。已实现的命令在临时仓库实际运行，复制输出，把每次运行都会变化的摘要和时间戳写成省略号或说明；尚未实现时标为预期输出，交付验收再核对实际运行，运行记录写进 Memory。错误写成表格，列出错误码和触发条件。`--json` 字段、错误码和退出码属于公开 Spec；人读输出帮助理解，不保证逐字稳定。同一输出或错误只在一个页面定义，其它页面链接过去。

行为页不写内部模块、内部数据结构、调用链、缓存或存储引擎；公开的输入输出结构、协议和可观察的恢复保证留在行为页。出现这些词时，把那段移到 architecture 或 data-model 页，行为页只保留使用者能观察到的保证，例如“删除缓存后结论不变”。architecture 页不重新定义行为；只改实现时只改 architecture 页。同一领域结构或错误被多个入口使用时只在一个行为页定义，其它页面只写自己入口的映射；能被打开阅读的内部文件不等于公开格式；性能预算只写在 Feature 的 `performance.md`。

正文写现行规则，不写“目前”“已实现”“这次改了什么”，不点名已删除的接口。Use Case 主流程的步骤加 `{#id}`，测试和实现可以指向具体步骤。路径与 anchor 是关系身份，链接目标写仓库相对路径或相对链接。

## 让第一次读的人读懂

Spec 的第一读者是没用过这个功能的人。Feature 的页面分三类，各回答一个问题：

| 页面 | 类别 | 回答 |
| --- | --- | --- |
| README、cli、library | 产品功能 | 谁用它、能做什么、怎么做；像使用教程一样写 |
| architecture | 技术架构 | 怎么实现：归属、数据流、不变量与资源生命周期 |
| Use Case | 用户旅程 | 在某个情形下，使用者做什么、看到什么 |

**Feature README** 按这个顺序写：

1. 开头两三句：谁会用它，它替使用者解决什么问题。
2. 「你可以做什么」：每项一句，用使用者的话写能力，不写机制。
3. 「上手」：一个照着就能运行的例子，命令按顺序给出，每步后面是读者看到的输出。
4. 「怎样工作」：使用者要正确使用必须理解的机制，配一张图解。
5. 「用户路径」：按使用者想做的事给 Use Case 分组。
6. 「细节」：链接到 cli、library 与 architecture 页。

输出字段、具名错误和退出码写在 cli 或 library 页，README 只链接它们。README 被源码锚点引用时，保留该标题，用一段使用者语言的概述加链接承接。

**按用户目标与处理路径组织 Use Case。** 每个 Use Case 写清起始状态、每步动作、要运行的命令或调用，以及看到的输出。用户目标或处理路径明显不同时另写一个 Use Case；同一路径中的输入变化与错误结果可以用表格说明，避免重复相同的步骤。例如 runner 状态未知后需要恢复，可以独立描述恢复路径；同一检查命令报告的不同字段错误可以放在结果表中。

**输出要真实。** 在临时 Git 仓库里实际运行命令，复制输出；每次运行都会变的摘要、时间戳和路径可以省略。尚未实现的行为标为预期输出。

**图解。** 多方协作、状态迁移、时序和数据流程用 p5 动画，静态结构用 Mermaid。先用文字写清规则，图解只演示已写下的规则，不新增规则，也不当作运行证据；不运行图解也要读得懂。

p5 采用流程动作循环：分阶段自动推进，当前阶段高亮，沿连线移动一个点表示传递，画面底部显示当前阶段的说明，一轮结束后从头开始。用 `p.describe` 写出整轮过程的文字描述；累计 `p.deltaTime` 并限制单帧增量，避免页面隐藏后跳过阶段。不加播放、暂停和单步控件，只有参数实验才加交互。一张图只讲一个过程。颜色从 `--concord-bg`、`--concord-accent` 等主题变量读取，图解随工作台主题变色，并与 Mermaid 图一致。外部入口路径相对所在 Markdown；扩展库统一配置在项目 `p5.libraries`，不在代码块里声明库或插入 CDN script。可复制的示例与沙箱边界见 `concord --skill view`。

**术语先定义，再使用。** 写下一个领域名词前，先在生效的 `concepts.md` 里找它：用 `concord concepts index --json` 或直接读所在目录及祖先目录的 `concepts.md`。找到了，就只用它的 term；找不到，先在合适的目录定义它，再写进 Spec。一个概念只用一种写法，不在中英两种写法之间切换；改名时把旧写法加进 `deprecated`，让检查找出全部旧写法。

**语言。** Spec 使用项目文档的主语言。命令、字段、错误码和代码标识写在行内代码中，不翻译、不改写成正文名词。

## 品味

品味是项目判断“什么是好的”的共同标准。每条品味一句话作标题，正文写它解决的问题，再给出好的样子与坏的样子；不写机制，也不写产品规则，产品规则写在 Feature，仓库自身的工程规则写在工程页。

品味条目写成 `## C-017 标题 {#c-017}`；总则用 `## 总则 {#general}`，其款用 `{#general-<name>}`。ID 一经采用不改名、不复用。依据某条品味的句子旁写指向其 ID 的行内链接，不用“第 N 款”这类序号文字；`concord check` 对指向不存在 ID 的链接报告 `AnchorNotFound`。

品味可以直接编辑，修改历史由 Git 保存。

## Design 与采用

了解现行行为只读 Feature、Use Case、cli、library、architecture 与 engineering 页。

Design 只用于真正难以取舍的问题，一页 `docs/design/<d>.md`：写清要决定什么、几种做法和各自的代价。定下来后把规则写进 Spec，删除这一页，理由写在提交说明里。不难取舍的问题直接改 Spec。

`roadmap start` 把 Roadmap 目录移入 `docs/feature/`，同时改写指向它的链接；目标已存在或采用期间文件发生变化时拒绝。

## 术语与写作规则

术语写在 `concepts.md`，写作规则写在 `writing.md`，都是普通 Markdown，放在哪个目录就对那个目录及其子目录生效；全局的放在 `docs/`。

`concepts.md` 的每个二级标题是一个概念：`## 订单 {#order}`，标题文字是唯一写法，下面第一段是定义；定义后以“旧写法：”开头的一段列出弃用写法，写在行内代码里，例如“旧写法：`单子`”。其余段落是解释。

`writing.md` 第一段写长度上限，例如“句子不超过 140 个字符，段落不超过 320 个字符”；“不用的词”是一张表：词、改成、为什么、只在哪些目录、例外；全局文件还可以有“检查范围”列表。

`concord docs check` 报告用错的词、超长的句子和没被用到的概念，逐处看上下文修改，不要机械全仓替换。精确格式见随包 docs/feature/documentation-quality/format.md。
