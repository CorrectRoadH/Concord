# Spec 与文档

先读本主题后附的文档模型与 Spec 写作示例，再写本次任务的正文。文档模型拥有分类、页面职责和身份规则；示例提供目录树及相互链接的成稿。两者来自安装资源，不要求接入项目存在 `docs/document-model.md` 或示例文件。

## 从目录树与成稿开始

1. 沿用用户已明确的目标与范围，读相关文档和必要的代码证据。
2. 按文档模型选择归属，用小目录树说明本次需要的页面。按需创建，不复制示例产品需求或整棵空目录。
3. 先完成一组可审阅的 README、Use Case 与必要细节页，再扩写同类页面。命令生成的骨架不是成稿。
4. 审阅读者能否完成目标、引用是否准确、未知项是否明确，再运行 `concord check`。修复 finding 并重跑至通过才完成；确实受环境、权限或文档写改范围阻塞时，明确报告未完成与所需条件。

只写文档的请求不授权修改业务代码、测试或配置。正式接入实现关联时，再读 `concord --skill code` 和 `concord --skill test`。

## 创建与发现

直接编辑文件即可；`concord new` 是可选的模板助手。先按内容选择页面，参数用 `concord new --help` 核对。例如界面功能可以创建：

```sh
concord new feature reading --pages ui,use-case
```

用 `concord list` 发现文档，`concord show <路径或选择器>` 读取正文及关系；选择器有歧义时使用完整路径。模板中的提示应替换为项目自己的正文。

## 让第一次读的人读懂

**README** 先写谁用它、解决什么问题，再给一条沿实际入口完成的上手路径和每步结果。界面产品写界面操作，命令或库产品写对应调用。随后解释使用者必须理解的规则，链接用户路径与细节页；字段、状态、错误和内部机制由各自细节页拥有。

**Use Case** 从一个用户目标出发，写起始状态、带稳定 `{#id}` 的步骤、可观察结果与完成判据。独立目标分别成篇，同一路径的输入变化和错误结果用表格说明。不要按内部接口逐项倒推用例，也不强行为界面用法添加命令。

**组合外部工具** 时，写清准备条件、产品交出的数据或入口、用户接下来怎样操作、各方职责及失败边界。命令和保证须有权威依据，未验证的路径标为预期用法。内部依赖选型归 architecture；删除产品能力前，确认原有用法如何继续满足需求。

**输出与证据**：在授权的隔离环境中核对实际界面或命令；动态时间、路径等可以规范化。尚未实现或未运行的结果明确标为预期。运行记录留在交付证据中；只有提炼出的可复用经验才进入 Memory。示例与图解不证明行为已经发生。

**图解**：先写清文字规则，多方协作、状态迁移、时序与数据流程用 p5 动画，静态结构用 Mermaid。图解只演示正文已有规则，不运行图解也要读得懂。p5 自动循环演示过程，用 `p.describe` 描述整轮过程，不默认添加播放或单步控制；主题、示例、扩展库与沙箱边界见 `concord --skill view`。

**性能**：声明操作、负载、参考环境、指标与阈值，链接项目自己的测量方法。不因使用 Concord 而指定语言、基准工具、统计量或文件布局；完整示例见本主题后附资料。

**语言与术语**：使用项目文档的主语言；命令、字段、错误码和代码标识写成行内代码。领域名词先在生效的 `concepts.md` 查找，找不到再定义；采用唯一 term，改名时记录旧写法。用 `concord concepts index --json` 查看派生汇总。

## 品味、术语与写作规则

品味写共同判断标准，说明问题、好的样子与坏的样子；产品行为归 Feature，工程规则归 Engineering。条目可写成 `## C-017 标题 {#c-017}`，ID 采用后不改名、不复用。在依赖某条品味的句子旁链接该 ID，历史由 Git 保存。

`concepts.md` 与 `writing.md` 是普通 Markdown，目录决定作用范围，全局文件位于 `docs/`。

- 概念用二级标题，如 `## 订单 {#order}`。标题是唯一 term，第一段是定义，其后是解释；旧写法用“旧写法：”段落列出，名称写成行内代码。
- 写作规则第一段写长度上限，例如“句子不超过 140 个字符，段落不超过 320 个字符”。“不用的词”表含词、改成、为什么、只在哪些目录、例外；全局文件可带“检查范围”列表。
- `concord docs check <path>` 检查所选路径的术语与写作问题。逐处看上下文修改，不机械全仓替换。

## 开放取舍与采用

困难且尚未决定的取舍写入 Design；已有授权内的常规选择自行收敛。定下后把规则写回所属 Spec，删除 Design，理由写在提交说明中。尚未采用的方向归 Roadmap；准备采用时按 `concord roadmap start --help` 核对迁移操作。
