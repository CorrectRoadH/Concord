# 照着 Spec 实现

实现指定的 Feature、Use Case 或步骤，让代码、测试和 Spec 一致。实现阶段不自行改变 Spec；完整开发任务需要修订时，先返回写 Spec 阶段，收敛后继续实现。分工任务遵守既定职责。

1. 读 Spec：`concord show <Use Case>` 查看步骤、已关联的代码与测试；读相关的 cli、library 与 architecture 页。
2. 先确认 Spec 够用：命名、行为、错误和验收方式都已写明，关键保证有观察入口与失败判据。缺失、自相矛盾或与代码事实冲突时，停下依赖它的部分，列出 Spec 位置、证据和可选做法，按职责返回写 Spec 阶段或交给负责人；只有缺少关键决定或授权才询问用户。其余不受影响的部分继续。
3. 实现并写测试，在能观察保证的最低层通过真实入口核对动作、结果与副作用。外部系统可在实际边界模拟，不以内部赋值或测试专用入口替代所验路径。测试加标记（`concord test marker`），实现加代码声明（`concord code marker`）；目标选择与语法见 `concord --skill test` 和 `concord --skill code`。
4. 按项目的验收方法准备隔离环境，确认数据、端口、实例与就绪条件，再运行相关测试和 Spec 要求的验证。正常与失败退出都回收本次创建的资源，保留取证材料；没有实际执行、被跳过或中止的检查不算通过。
5. 运行 `concord check` 与 `concord trace gaps`，处理本次引入的关系问题及必要依赖，报告其它缺口；关联不表示覆盖。把 Spec 中标为预期输出的示例与实际运行对照，不一致时按第 2 步处理，不为适应错误实现改写 Spec。

## 使用形式验证时

逐项核对模型动作与当前代码，尤其是原子步骤、分支、取值范围和写入同一共享状态的新路径。代码结构变化后更新验证描述；性质变化必须有 Spec 依据，不能为通过而削弱性质或缩小探索边界。需要改 architecture 等 Spec 时，按第 2 步交回。

分别确认模型能检出所声明的故障、模型描述当前代码、真实实现满足验收。故障注入使用隔离副本，完成后清理；独立手写模型不会因产品代码被改坏就自动失败，不能将修改模型的失败当成代码验证结果。

反例用领域语言列出初始条件、事件序列、违反的规则和后果，逐步对照代码，并在可行时实际复现。步骤无法发生时先检查模型；确为实现违反 Spec 时修复实现，环境或工具阻塞单独报告。工具版本与复跑命令沿用项目约定。

交付时给出改动、运行的命令与结果、证据位置、仍未满足的 Spec 条目和未回收资源。采用模型时说明假设、探索范围及未覆盖项，区分模型偏离与产品缺陷；测试或模型通过不等于 Spec 全部满足。
