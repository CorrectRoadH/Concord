# 写 Spec

把一个需求写成实现者不用再问的 Spec。只改 `docs/`，不写实现代码。先读 `concord --skill document` 提供的 docs 目录树和完整成稿示例，再按本项目目标写作。

1. 读现状：`concord list feature`、`concord show <相关 Feature>`，读 `docs/taste.md` 与生效的 `concepts.md`。找出需求落在哪个 Feature；没有合适的就新建。
2. 写行为：先明确谁想完成什么，再用 Use Case 写满足需求的具体用法：起始状态、带 `{#id}` 的操作步骤、看到的结果和完成判据。步骤按实际入口写界面操作、命令、调用或外部工具配合，不按现有接口逐项倒推用例。Feature README 像使用教程；同一路径的输入变化和错误写成表格。尚未运行验证的结果标为预期结果。
   组合外部工具时，写清准备条件、交接的数据或入口、各方职责和失败时的可观察结果；核对工具文档，不虚构命令与保证。先盘点已有用法与界面价值，再判断哪些基础能力应复用，不能仅因外部工具也有图表就删除产品的检视能力。写法与案例见 `concord --skill document`。
3. 定下实现者会问的事：Use Case 路径写完后，再定公共命名、输入输出字段、具名错误与退出码，写在 cli、library 或 api 页，每个公开名字都能指回一个用户目标；实体归属、数据流、不变量与资源生命周期写在 architecture 页。新名词先进 `concepts.md`，代码里的类型、字段、表名、诊断值与事件名沿用同一个名字；并列选项按决定行为的那一维命名，不用对每个选项都成立的词。
   涉及并发、重试、取消、恢复或资源所有权时，按风险写清合法迁移、禁止状态、终止条件和失败后保留的状态。可观察保证归行为页，内部不变量与原子动作归 architecture；图解只解释正文已有的规则。
4. 确定验收方式：关键保证写清前置条件、触发动作、观察入口、预期结果和失败判据。涉及持久化、消息或资源释放时，同时核对副作用；简单行为用已有步骤与结果表表达，不另建清单。选择能观察结果的最低测试层；启动、隔离、取证、清理和复跑方法归项目的 Engineering 页。
5. 有几种做法都说得通且尚未决定时，写 `docs/design/<d>.md` 列出做法与代价；已有授权内的常规选择自行收敛，只有未获授权的关键取舍才请维护者决定。定下后把规则写进 Spec 并删除这一页，不难取舍的直接写进 Spec。
6. 运行 `concord check`，处理本次引入的 finding 及必要依赖，报告其它既有问题。它检查文档结构与关系，不执行行为验收。

## 按风险选择验证

普通行为使用测试，输入组合可以用性质测试。高后果且测试难触达的事件交错可以用模型检查；需要超出有限边界的保证时再考虑证明工具。不默认要求形式验证或指定某一种工具。

采用形式验证时，在所属 Spec 写清所验性质、环境假设、探索边界与未覆盖项；最终完成的保证还需说明调度与公平性前提。高风险保证写明验证应能检出的故障，例如漏掉校验或提前释放锁。这里确定要求，验证程序、故障注入与反例复现由实现阶段完成。

模型通过只说明该模型在声明条件下满足性质，不能代替代码一致性检查与真实实现的验收。Spec 拥有保证，测试或模型拥有可执行定义与关联；不在 skill 中再维护功能地图、覆盖清单或同步历史。

交付时说明改了哪些页、定下的行为与验收方式、证明边界，以及仍待决定的问题。预期输出与图解不是运行证据。页面写法的完整规则见 `concord --skill document`。
