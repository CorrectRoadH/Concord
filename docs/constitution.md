# Concord 的品味与底线

品味是这个项目判断“什么是好的”的共同标准：规则写不到的地方按品味选择，审阅时按品味判断好坏，可以链接某条品味指出变化哪里不合品味。底线是不得违反的硬约束。功能细节由 Feature 与 Use Case 拥有，跨功能机制由[架构](architecture.md)拥有，页面职责由[文档模型](document-model.md)拥有，agent 操作细则由 `AGENTS.md` 拥有。

## 总则 {#general}

1. 品味说明它解决什么问题、好的样子和坏的样子。它是判断标准，不是逐条检查的规则；品味之间需要取舍时，在变化说明或 Memory 中写明理由。 {#general-taste}
2. 底线中“必须 / 不得”是硬约束，违反即阻止交付；未使用这些词的规范性陈述同样有约束力，“可以”表示允许。底线全部同时成立，确实无法同时满足时，先修订再采用。 {#general-paragraph}
3. 每条底线陈述一项跨功能规则，标题就是规则本身；每款一项可审阅的义务、禁止或许可。 {#general-one-rule}
4. 品味与底线都不写达成它们的机制。实现方式写在所属 Feature 的 architecture 页，产品行为写在行为页，仓库维护机制写在工程页。 {#general-rules-only}
5. 用现行句式，不描述与过去的差别。 {#general-present}
6. 依据某条品味或底线的句子旁写指向其 ID 的链接，不用“第 N 款”这类序号文字。ID 一经采用不改名、不复用；修订后检查链接被修改 ID 的页面。 {#general-link}
7. 本文件可以直接编辑。每次修订在同一变化中附一条 Decision Memory，写明适用范围、理由、来源与影响，并以 `amends` 指向受影响的条目；本文件只保存当前正文，修订历史从 Memory 与 Git 派生。新发现的跨功能约束通过修订写入，功能专属细节留在对应 Spec。 {#general-amend}

## 品味

## C-017 读得懂胜过写得全 {#c-017}

Spec 没人看得懂，就没人认真审阅，也就没人维护。

- 好的样子：README 像使用教程，先讲能做什么，再给一个照着就能运行的例子；功能在不同情形下的表现各写成一个 Use Case；多方协作与状态变化配一张 p5 动画。
- 坏的样子：README 开头就是字段、退出码和边界条件；用一串子规则枚举各种情形。

## C-018 一个词一个意思 {#c-018}

人和 AI 用不同的词说同一件事，或用同一个词说两件事，读者只能猜。

- 好的样子：领域名词先在 `concepts.md` 定义再使用；改名时留下弃用名；命令、字段和错误码写在行内代码里；一个页面只用项目文档的主语言。
- 坏的样子：快照与 snapshot 混用；“发布”同时指写入的提交和软件发版；页面在中英文之间切换。

## C-019 一件事只写一次，其余推导 {#c-019}

同一事实的多份副本迟早不一致，手工维护的登记表总会过期。

- 好的样子：每项事实只有一个 owner，其它页面链接它；反向关系、索引和汇总从来源推导；缓存随时可以删除，删除后结论不变。
- 坏的样子：手工 INDEX；第二份关系清单；同一个错误码在两个页面各定义一遍。

## C-020 写现在，不写过去 {#c-020}

历史叙述让人和 agent 把旧规则当成现行规则，兼容层让系统同时存在两套真相。

- 好的样子：Spec 只声明当前行为；排障经过、进度和交接写进 Memory；格式变化时直接改写文件。
- 坏的样子：“目前”“已改为”“旧版本”；迁移说明；为旧格式保留的读取路径。

## C-021 只声称证明过的 {#c-021}

没有证据的“已修复”“已覆盖”，会让人放心地出错。

- 好的样子：修复在缺陷提交和修复提交上各验证一次，结论写明证明了什么、没有证明什么；标记表示关联，不表示覆盖。
- 坏的样子：“check 通过，所以功能完成”；用一次运行代表所有情形。

## C-022 文件是界面，命令只是助手 {#c-022}

只能通过工具修改的状态不透明，也把使用者锁在工具里。

- 好的样子：全部内容是 Git 中的普通文件，人和 agent 直接编辑；命令只执行必须运行的步骤，并把结果写回文件；门禁判断变化是否合法。
- 坏的样子：必须经过某个命令才能修改的状态；只存在于数据库里的事实。

## C-023 快到每次都愿意跑 {#c-023}

慢的检查会被跳过，被跳过的检查等于没有。

- 好的样子：高频命令有性能预算；先测量、定位瓶颈再优化；命令只读取完成目标所需的输入。
- 坏的样子：为了更快跳过校验；没有测量就改实现。

## C-024 规则少而硬，机制留给实现 {#c-024}

规则越长越没人读；把机制写进规则，改实现就得修规则。

- 好的样子：每条品味一句话，配好坏对照；底线只写必须和不得；机制写在 architecture 页。
- 坏的样子：在品味或底线里写句柄、租约、Schema 版本和注释前缀。

## 底线

## C-002 独立、本地、可安装 {#c-002}

1. Concord 必须作为独立安装包在隔离 Git 消费者中工作，不依赖其它仓库的 checkout、全局安装、provider 凭据或部署服务。 {#c-002-1}
2. 可选外部接入必须有明确边界，不成为基础本地流程的前提。 {#c-002-2}
3. 本地 Issue 不依赖外部服务。远端写入需单独授权，本地操作不自动投射为远端变更。 {#c-002-3}

## C-003 写入遵守范围和恢复 Spec {#c-003}

1. 所有写入必须校验目标路径、前像与完整变更集，拒绝路径逃逸和 symlink 绕过。 {#c-003-1}
2. 中断时必须保留可解释的恢复现场，不覆盖未知编辑。 {#c-003-2}
3. 新增配置、来源和写入口必须同时定义资源所有权与恢复授权。 {#c-003-3}

## C-005 维护代码采用严格 TypeScript 与 Effect {#c-005}

1. 实现、测试和构建脚本采用严格 TypeScript，执行与副作用通过 Effect 组织。不添加手工维护的 JavaScript，不绕过类型检查；编译输出和 JavaScript 消费者兼容 fixture 除外。 {#c-005-1}
2. Effect 依赖精确固定，使用 API 前读取安装包指引。不可信边界严格 Schema 解码并返回具名失败。 {#c-005-2}
3. 唯一原生例外是 `native/hawdb`：Rust N-API 桥接、链接胶水、字节转换、预算执行与固定 revision 的目录所有权锁适配。领域决策、来源核验、测试和构建编排仍属 TypeScript/Effect。 {#c-005-3}
5. 本条约束 Concord 自身。接入项目的语言、包管理器和运行时由其自行选择。 {#c-005-5}

## C-006 用产品自身管理和验收开发 {#c-006}

1. 新功能先声明目标 Feature 与完整 Use Case，重要方案经 Design 比较和裁决。 {#c-006-1}
2. 验收测试在声明旁关联 Spec。交付必须通过 `pnpm check`，通过构建与打包后的公开 CLI 在隔离 Git 消费者中验证。 {#c-006-2}
3. Concord 的 check、trace 与 review 用于检查自身关系，不虚构测试关联或完成状态。 {#c-006-3}

## C-007 尊重协作与外部操作授权 {#c-007}

1. 保留其他任务的改动，控制写入范围。 {#c-007-1}
2. 未经明确授权不得 push、发布、操作生产、调用付费模型或发送外部消息。 {#c-007-2}
3. 破坏消费者兼容、改变持久数据含义、重划资源所有权或信任边界、回滚依赖协调迁移的方案，必须先完成独立设计挑战：由未参与方案的 reviewer 只读审查并给出书面结论，存在未解决的阻断意见时不得定案。 {#c-007-3}
4. 凭据只从环境变量或外部工具登录态读取，不写入 docs、配置、缓存、证据、HTTP 响应或诊断。 {#c-007-4}

## C-015 机器可读输出是公开 Spec {#c-015}

1. `--json` 输出结构、具名错误码与退出码是 agent 和脚本依赖的公开 Spec，由对应 Feature 的 CLI 页面或 Use Case 声明。 {#c-015-1}
2. 删除或改变已声明字段、错误码与退出码含义属于破坏消费者兼容，按 [C-007](#c-007-3) 处理；新增字段不改变既有字段语义。 {#c-015-2}
3. 人读输出不是 Spec，消费者不解析人读输出。 {#c-015-3}
