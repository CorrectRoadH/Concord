# Concord 项目宪法

本宪法规定 Concord 跨功能、长期有效的开发规则，以及 Concord 要求接入项目采用的工作范式。功能细节由 Feature 与 Use Case 拥有，跨功能机制由[架构](architecture.md)拥有，方案比较与裁决由 Design 拥有，agent 操作细则由 `AGENTS.md` 拥有。宪法只确立规则，不陈述代码是否已经符合。

## 总则 {#general}

**适用范围。** 规则适用于生产代码、测试、构建脚本、随包模板与 skill，以及 `docs/`。标明“接入项目”的条款同时约束使用 Concord 的消费仓库。

**用语强度。** “必须 / 不得”是硬约束，违反即阻止交付。未使用这些词的规范性陈述同样有约束力。“可以”表示允许。

**冲突处理。** 硬约束同时成立。写入安全与授权（[C-003](#c-003)、[C-007](#c-007)）、证据真实（[C-004](#c-004)）、事实唯一（[C-001](#c-001)）和性能（[C-014](#c-014)）依次用于选择满足全部硬约束的方案，不授权违反其它条款。确实无法同时满足时，按 [C-008](#c-008) 修订后采用。

**条款写法。**

1. 每条款陈述一项跨功能规则，标题就是规则本身。 {#general-one-rule}
2. 每款一项可审阅的规则：义务、禁止或许可。未写“必须”“不得”的规范性陈述同样有约束力。 {#general-paragraph}
3. 条款写约束，不写达成约束的机制。明确采用的技术栈、依赖固定、信任与资源边界属于约束；实现方式写在 architecture 页，理由、来源与影响写在修订对应的 Decision Memory，过程写在 Memory。 {#general-rules-only}
4. 用现行句式，不描述与过去的差别。 {#general-present}
5. 依据某条规则的句子旁写指向其 ID 的链接，不用“第 N 款”这类序号文字。 {#general-link}

## C-001 事实只由自己的来源维护 {#c-001}

1. 每项事实只有一个 owner。Spec 正文由 Markdown owner 拥有；领域术语由 docs 下按目录归属的 `concepts.md` 拥有，写作政策由同目录的 `concord-writing.json` 拥有；测试定义与正向关系由测试源码拥有。Issue 拥有工作项的状态、关系与关闭结论，Memory 拥有知识的正文、类型、状态与关系；生命周期的文本历史在 Git。 {#c-001-1}
2. 目录确定术语与政策的局部作用域，docs 根拥有全局定义。术语的定义与解释写在同一 `concepts.md`；其它 Markdown 链接到定义，不重复维护。 {#c-001-2}
3. 反向关系、聚合索引与引用反查从来源派生，不维护第二份登记表。 {#c-001-3}
4. HawDB 只保存可重建投影与可丢弃缓存，短期解析使用同一引擎的内存实例。文件 owner、证据与发布日志不进入缓存。 {#c-001-4}
5. 人与 Agent 直接编辑 `docs/` 与 `memory/` 下的文件，包括 Memory 与 Issue；索引、检索与反向关系由 Concord 从文件派生，不维护人工 INDEX。状态、关系与关闭结论的合法性由 `concord check --since <base>` 门禁检查，Concord 命令是执行需要运行的步骤的助手。 {#c-001-5}

## C-002 独立、本地、可安装 {#c-002}

1. Concord 必须作为独立安装包在隔离 Git 消费者中工作，不依赖其它仓库的 checkout、全局安装、provider 凭据或部署服务。 {#c-002-1}
2. 可选外部接入必须有明确边界，不成为基础本地流程的前提。 {#c-002-2}
3. 本地 Issue 不依赖外部服务。远端写入需单独授权，本地操作不自动投射为远端变更。 {#c-002-3}

## C-003 写入遵守范围和恢复 Spec {#c-003}

1. 所有写入必须校验目标路径、前像与完整变更集，拒绝路径逃逸和 symlink 绕过。 {#c-003-1}
2. 中断时必须保留可解释的恢复现场，不覆盖未知编辑。 {#c-003-2}
3. 新增配置、来源和写入口必须同时定义资源所有权与恢复授权。 {#c-003-3}

## C-004 证据只表达实际证明的范围 {#c-004}

1. 源码声明不等于执行，命令成功收据不等于逐 case 覆盖或正式 E2E 可靠性。 {#c-004-1}
2. Issue 标记为 fixed 时，同一冻结命令必须在缺陷候选上以非零结果结束、在被接受的快照上通过，两者之间测试、runner 输入与所指 Spec 不变。核验结论写入 Issue，可在声明的输入与环境下重放；command 结果不证明逐 case 执行。 {#c-004-2}
3. 文档、宪法结构或关系检查不得被展示为实现合规、功能完成或测试覆盖的证明。 {#c-004-3}

## C-005 维护代码采用严格 TypeScript 与 Effect {#c-005}

1. 实现、测试和构建脚本采用严格 TypeScript，执行与副作用通过 Effect 组织。不添加手工维护的 JavaScript，不绕过类型检查；编译输出和 JavaScript 消费者兼容 fixture 除外。 {#c-005-1}
2. Effect 依赖精确固定，使用 API 前读取安装包指引。不可信边界严格 Schema 解码并返回具名失败。 {#c-005-2}
3. 唯一原生例外是 `native/hawdb`：Rust N-API 桥接、链接胶水、字节转换、预算执行与固定 revision 的目录所有权锁适配。领域决策、来源核验、测试和构建编排仍属 TypeScript/Effect。 {#c-005-3}
4. 桥接、引擎、Rust toolchain 与依赖精确固定。持久句柄由明确的唯一所有者管理，来源快照不拥有跨请求句柄；客户端的逻辑会话、事务、快照与清理的生命周期分别声明，内存句柄按进程管理。缓存不参与来源发布或证据裁决。发行包携带目标平台产物，消费者不需要 Rust、全局 HawDB 或数据库服务。锁协议与上游 revision 绑定，升级必须重新验证互斥与清理。 {#c-005-4}
5. 本条约束 Concord 自身。接入项目的语言、包管理器和运行时由其自行选择。 {#c-005-5}

## C-006 用产品自身管理和验收开发 {#c-006}

1. 新功能先声明目标 Feature 与完整 Use Case，重要方案经 Design 比较和裁决。 {#c-006-1}
2. 验收测试在声明旁关联 Spec。交付必须通过 `pnpm check`，通过构建与打包后的公开 CLI 在隔离 Git 消费者中验证。 {#c-006-2}
3. Concord 的 check、trace 与 review 用于检查自身关系，不虚构测试关联或完成状态。 {#c-006-3}

## C-007 尊重协作与外部操作授权 {#c-007}

1. 保留其他任务的改动，控制写入范围。 {#c-007-1}
2. 未经明确授权不得 push、发布、操作生产、调用付费模型或发送外部消息。 {#c-007-2}
3. 破坏消费者兼容、改变持久数据含义、重划资源所有权或信任边界、回滚依赖协调迁移的方案，必须先完成独立设计挑战：由未参与方案的 reviewer 只读审查并给出书面结论，存在未解决的阻断意见时不得定案。 {#c-007-3}
4. 凭据只从环境变量或外部工具登录态读取，不写入 docs、配置、缓存、证据、HTTP 响应或诊断。 {#c-007-4}

## C-008 宪法随功能经验明确修订 {#c-008}

1. 功能规划、实施和审阅读取当前宪法。新发现的跨功能约束通过修订写入；功能专属细节留在对应 Spec。 {#c-008-1}
2. 修订须按项目授权采用，说明适用范围、理由、来源和影响。宪法可以直接编辑；每次修订的同一变化中有一条 Decision Memory 记录这些内容，并以 `amends` 关系指向受影响的条款；宪法文件只声明当前规则与采用状态，不保存修订历史，历史从 Memory 与 Git 派生。 {#c-008-2}
3. 正文只维护当前规则，修订时直接改写，不追加相反规则，不声称已有功能自动满足新规则。 {#c-008-3}
4. 条款与款的身份由 ID 拥有，ID 一经采用不改名、不复用，不设版本号。修订后必须检查链接被修改 ID 的页面。 {#c-008-4}

## C-009 只有当前格式，没有历史包袱 {#c-009}

1. 配置、owner、journal、证据与缓存只有当前格式。运行时只按当前 Schema 严格解码，其它输入按无效输入返回具名解码错误；不识别旧版本，不提供迁移命令、兼容读取或双轨模型。无法解码的 journal 与锁保留现场并阻断写入，不被普通恢复删除。 {#c-009-1}
2. 格式变化时，Concord 自身仓库与接入项目把文件直接改写为当前格式，缓存与可重建投影直接丢弃重建。缺少当前绑定的证据必须重新取证，不补字段或重算摘要伪装为当前证明。 {#c-009-2}
3. 宪法、Spec 与指南只描述当前格式与行为，不描述格式如何变化，也不说明如何从旧格式过渡。 {#c-009-3}
4. 本条约束格式边界，不改变领域数据的含义。 {#c-009-4}

## C-010 接入项目采用 Concord 范式 {#c-010}

1. Concord 规定一套工作范式，接入项目必须采用：统一 Spec 布局；Spec 先于实现；每项事实一个 owner；`docs/` 只写声明（[C-012](#c-012)）；测试与实现通过显式源码标记关联 Spec。工程过程进入 Memory 与 Issue；Issue 按关闭种类的规则关闭，fixed 经过修复核验；写入遵守前像与恢复 Spec。 {#c-010-1}
2. 不提供关闭事实归属、关系解释、生命周期、证据下限及安全写入不变量的配置。项目可以配置来源位置、执行适配、文档页面和写作规则参数，配置不得绕过已采用的不变量。 {#c-010-2}
3. `concord check` 必须执行关系、生命周期及项目写作政策检查；检查失败或必需输入缺失时返回非零退出码，并区分违规与输入不完整。必查范围、必需规则与接入条件由[文档写作 Spec](feature/documentation-quality/README.md)声明；定向检查或独立 profile 的结果不能替代聚合门禁。聚合检查不成为局部读取和修复操作的前提。 {#c-010-3}
4. 范式不规定技术栈。产品构建与部署、原生 runner、运行环境、语言与包管理器由接入项目拥有；通用模型不要求产品包名、私有 HTTP 接口、Nx metadata 或 host/provider 分类。可选执行能力缺失只阻断需要它的操作，不使静态 Spec 与关联失效。 {#c-010-4}
5. 关闭种类的要求是关闭结论的下限，不能通过换入口或删除配置绕过。修复核验由 Concord 统一执行；runner 与 adapter 负责真实执行与资源终结，范式不要求所有项目采用同一 runner。 {#c-010-5}
6. 政策变更与跨仓库切换必须保留历史原件、互斥和恢复边界，不得形成并行授权域或降低既有关闭要求。 {#c-010-6}

## C-011 关联由源码声明拥有，指向最小完整范围 {#c-011}

1. 测试根中的 Concord 标记是测试关联的唯一正向来源，标记存在即关联存在。静态关联扫描不解析宿主语言的测试声明、框架绑定、回调或 skip/todo。执行时的原生收集、绑定与选择仅按 [C-011](#c-011-6) 进行，其观察结果不创建关联，也不授权静态关系检查成功。 {#c-011-1}
2. 实现关联的唯一正向来源是通过语法、作用域、位置与目标校验的显式代码声明。未通过校验的标记产生 finding，不建立关联。反向关系从测试标记与代码声明派生。 {#c-011-2}
3. 测试与实现指向能完整、准确描述该测试断言或该声明职责的最小既有 Spec 范围。测试可以指向 Feature 或 Use Case owner、Use Case 步骤，以及它们的附页或标题 anchor；实现还可以指向 Engineering owner 及其附页。对使用者可观察的保证先写进行为页再关联。只服务内部不变量的代码与测试，指向所属 Feature 的 architecture 或 lifecycle 页的 anchor；仓库维护机制的代码指向 Engineering。跨步骤的完整断言指向整个 Use Case，一个声明服务多项行为时使用多个 implements。没有合法目标的测试不建立关联，不为此伪造产品步骤。 {#c-011-3}
4. 代码侧选择完整且受支持的语义范围。整个文件服务同一职责且没有更精确的适用目标时，使用文件级声明。不为追求更窄而拆分实现、复制测试或机械改名步骤。缺少逐步骤关联不说明缺少执行或覆盖。 {#c-011-4}
5. JS/TS 仅用注释范围排除字符串和模板中的伪标记；其它文本文件接受以 `//`、`#` 或 `--` 开头的标记行。 {#c-011-5}
6. 执行由接入项目的 runner 命令或显式配置的 adapter 负责。adapter 可以仅在显式收集或执行前，把源码标记绑定到观察到的原生用例集合，或使用源码标记中的显式原生选择参数。原生选择不参与关联身份，不产生关联，不使静态检查依赖观察。只有能力和当前输入足以证明精确选择时，才声明选中了原生用例；否则执行范围按文件明确展示，要求原生精确选择的操作具名失败。缺少逐用例选择能力不使源码关联失效。 {#c-011-6}

## C-012 Spec 写可观察行为，实现与过程各归其位 {#c-012}

1. 行为页（Feature README、Use Case、cli、library）用使用者的语言声明输入、可观察结果、错误与约束。公开的输入输出结构、协议、机器可读字段、具名错误码、退出码，以及使用者可观察的持久化与恢复保证，属于行为页。行为页不写内部模块、内部数据结构、调用链和引擎选型。 {#c-012-1}
2. 规范性陈述应能被测试断言。命令页给出完整调用、机器可读输出、退出码、具名错误与最小示例；API 页给出签名、返回值与失败。人读输出示例用于理解，可以规范化动态值，不保证逐字稳定（[C-015](#c-015-3)）。实现之前的示例标为预期输出；交付验收核对实际运行，运行记录进入 Memory，示例不作为运行证据。同一输出或错误定义只在一个行为页维护，其它页面链接引用。 {#c-012-2}
3. architecture 与 lifecycle 页声明该 Feature 的内部实现：实体归属、数据流、不变量、失败阶段与资源生命周期。它们随实现修改，不重新定义行为。跨 Feature 的系统边界写在项目 `docs/architecture.md`。只改内部实现的修改不改行为页。 {#c-012-3}
4. Roadmap 与 Feature 同体裁，表示尚未采用的方向，其示例均为预期输出。实现与测试不指向 Roadmap。 {#c-012-4}
5. 约束用现行句式表达，只描述当前规则，不描述它与过去的差别，不点名已删除的接口、实现或文档。Design 的历史方案记录按裁决时的陈述理解，不因本款被解释为当前要求。 {#c-012-5}
6. 实施日志、进度、待办、排障经过、测试运行记录、审阅与挑战经过、提交收据和 agent 交接不进入 `docs/`。排障经过、根因和可复用经验归 Memory，待调查的观察归 Issue，正式采用的目标归 Spec。Research 的研究事实、Design 的候选与裁决，以及记录类 owner 由工具维护的生命周期元数据，由各自 owner 保留，不借此记录实施日志、审阅经过或交接。本规则不授权删除或改写既有证据、来源及生命周期历史；Design 记录与 Spec 的分工见 [C-012-7](#c-012-7) 至 [C-012-10](#c-012-10)。 {#c-012-6}
7. 已裁决 Design 的候选、共同约束、验收与裁决正文是裁决时的方案记录，不作为现行 Spec 的 owner。 {#c-012-7}
8. 裁决时，选中方案中仍适用的要求完整写入相应的行为页、architecture 页或工程页；此后这些要求在 Spec 中维护，不因实现尚未满足而丢弃。 {#c-012-8}
9. Design 不为追随实现改写历史方案。经授权的理由更正与内容组织调整，仍遵守已有的来源保留、身份与生命周期规则。 {#c-012-9}
10. Spec 对 Design 的引用只用于导航或说明决策依据；链接目标的检查范围由 [documentation-quality 的聚合门禁](feature/documentation-quality/README.md#聚合门禁)声明。 {#c-012-10}
11. 声明式 owner（Feature、Use Case、Engineering、宪法、`concepts.md` 与写作政策）只保存当前声明，不保存创建时间、采用来源、修订日期或修订历史。这些事实由 Git、Memory 或记录类 owner（Research、Design、Roadmap、Issue、Memory）保存，需要时派生。 {#c-012-11}

## C-013 操作依赖、发布协调和证据裁决分别定义 {#c-013}

1. 每个操作按目标与不变量声明所需输入。局部读取与精确引用验证不以无关 owner、代码或测试全部有效为前提；目标身份、来源、归属与路径安全仍须严格校验。 {#c-013-1}
2. 全局诊断保留可读取记录和全部已发现错误。完整性随投影与关系输出传播，不完整输入不能授权依赖完整图的裁决。 {#c-013-2}
3. 只读来源访问使用乐观快照并核验观察集合和发布代次；普通写入规划不持锁，提交使用短期独占协调与前像核验；dry-run 表达变更预览，与访问权限分别建模。未知 runner 清理状态阻断发布。 {#c-013-3}
4. 恢复区分 journal 结果、实际回收 token 与 runner 状态，返回成功前核验恢复后的协调状态，不用无 journal 推断仓库整体可写。 {#c-013-4}

## C-014 性能是交付约束 {#c-014}

1. Concord 是 agent 高频调用的本地工具。高频公开操作必须具有由其 Spec owner 声明的性能预算。[性能验收](engineering/concord-self-hosting/performance.md)统一声明参照环境、数据规模、冷暖状态、测量边界、采样方法及失败判据；超预算或缺少必需测量证据均不能判为通过。 {#c-014-1}
2. 命令只读取完成目标所需的输入，不为只读操作加载无关子命令、启动无关进程或扫描无关 owner。所需输入包括安全、来源一致性及完整性验证所需的全部输入。 {#c-014-2}
3. 优化前必须测量并定位瓶颈，优化后用同一方法复测；测量结果进入 Memory，预算与方法进入 Spec。不得为性能跳过摘要或 Schema 校验、路径安全、完整性门禁、授权检查，或缩减全局诊断范围。 {#c-014-3}
4. 当前事实查询的缓存只加速，成功结果的领域事实与有效性判断必须与同源重建一致，不返回陈旧或未经校验的成功结果。Spec 明确声明为历史投影的只读查询可以返回带构建时间、来源一致性与完整性标注的结果，未知关系标为未知；该结果不表示当前来源有效，不得授权 check 成功、写入、恢复或证据裁决。投影的刷新、漂移与不可用语义由对应 Spec 拥有。 {#c-014-4}

## C-015 机器可读输出是公开 Spec {#c-015}

1. `--json` 输出结构、具名错误码与退出码是 agent 和脚本依赖的公开 Spec，由对应 Feature 的 CLI 页面或 Use Case 声明。 {#c-015-1}
2. 删除或改变已声明字段、错误码与退出码含义属于破坏消费者兼容，按 [C-007](#c-007-3) 处理；新增字段不改变既有字段语义。 {#c-015-2}
3. 人读输出不是 Spec，消费者不解析人读输出。 {#c-015-3}
