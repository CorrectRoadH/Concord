# 测试架构

测试是 Use Case 验收的可执行证据（[C-006](../../constitution.md#c-006-2)）。一个好的测试在行为被破坏时失败，在行为不变的重构后仍然通过，结论不受机器负载影响，成本与它守护的行为相称。本页规定测试如何满足这四点；执行入口、并发与共享资源见[测试执行与浏览器验收](testing.md)，性能基准见[性能验收](performance.md)。

## 质量标准

| 标准 | 规则 |
| --- | --- |
| 指向验收 | 每个产品测试用标记指向一个 Feature、Use Case 或其步骤；仓库自身的检查（例如架构测试）暂不带标记，测试名写成它验证的那条验收。一个测试验证一条验收；失败消息带输入、期望与实际，能直接定位到那条验收 |
| 断言可观察结果 | 只通过公开入口断言：CLI 的 `--json` 结果与退出码、HTTP 响应、库 API 的返回值、仓库文件的字节。不断言内部函数是否被调用、私有状态或日志措辞 |
| 会失败 | 新测试在交付前至少对未实现或故意回退的实现运行一次并失败，交付说明记录这次失败。修复 Problem 的回归测试按 command evidence 的 red/green 取证 |
| 确定 | 不依赖时长、调度顺序、机器负载或网络；时钟、端口与随机数由测试注入或向系统申请。等待真实的产品状态，超时只用于发现挂起 |
| 便宜 | 在能观察到该结果的最低一层测试，单个测试与整个门禁都有成本上限，见[成本与稳定](#成本与稳定) |

## 分层

每条验收在能观察到其结果的最低一层测试。上一层只为该层新增的边界写测试，不重复枚举下层已经覆盖的领域情形。

| 层 | 边界 | 适用 | 单个测试 p50 上限 |
| --- | --- | --- | ---: |
| 纯函数 | 内存中的输入，直接调用领域函数 | 解析器、Schema、写作规则、关系推导、trace 编译、步骤与锚点、路径规范化 | 50ms |
| 仓库内 | 真实临时 Git 仓库，进程内调用 LocalRepository 与领域操作 | 发布、journal 与恢复、CAS、路径安全、缓存命中与失效、Memory 与 Issue 生命周期 | 1s |
| 构建 CLI | `dist` 的 CLI 子进程，隔离消费者 | 参数与帮助、`--json` 结构、退出码、具名错误、人读输出的呈现 | 2s |
| 进程与生命周期 | 多个进程、信号、原生模块、安装包、常驻服务 | 并发与互斥、崩溃与恢复、工作区服务、离线安装、跨平台产物 | 10s |
| 浏览器 | e2e engine 拥有的真实浏览器 | Web 工作台的用户路径、导航、草稿保护、呈现 | 20s |

上限按[统一方法](performance.md)的参照机器空闲时测量，进程与生命周期层的上限不含被测进程自身声明的超时。

每层测试的被测对象固定：纯函数层与仓库内层从 `src/` 导入，经 tsx 运行，与 `pnpm concord` 运行源码的方式相同，不需要构建；原生产物取自共享缓存。构建 CLI 层只运行本次调用构建的 `dist` 中的 bin；进程层还可以运行由 Installation 定位的工作进程入口，测试不导入 `dist` 的模块，也不依赖它的内部文件布局。发布内容由一个打包测试验证：打包、安装一次，核对文件清单与从安装包启动。唯一的例外是验证[从源码运行](README.md#从源码运行)与原生构建、绑定边界的工程检查：它们属于进程层，但运行源码入口或使用共享缓存中的原生产物，同样不依赖 `dist`。

构建 CLI 层的规则：每个命令、每个具名错误码与每个退出码至少有一个构建 CLI 测试；同一领域行为的其它情形（例如 Use Case 验收表中的多行）在纯函数或仓库内层逐行测试。构建 CLI 层不承担领域情形的穷举。

fake 只用于外部边界：GitHub 与其它远端服务、模型、系统浏览器之外的网络。领域函数的输入可以是内存中的字符串与文件集合，这不是 fake；不为 Concord 自己的模块写 fake 或 mock。

## Fixture

测试仓库由 `test/support` 中的一个 fixture 模块构造。每次测试运行先构建一个已初始化的模板消费者，每个测试复制模板得到自己的仓库，不在每个测试中重新执行 `git init` 与 `concord init`。需要不同初始状态的测试在复制后通过公开入口修改。

受管文件的内容只由格式的 owner 生成：Spec 与 Memory 通过领域写入入口或 `renderDocument`，宪法通过 `initialConstitution`，配置通过配置渲染函数，写作政策与 concepts 通过各自的写入入口。测试源码不手写受管格式的 frontmatter、配置或 JSON。格式改变时只改格式 owner，测试不随之修改（[C-009](../../constitution.md#c-009-2)）。

例外是验证无效输入的测试：它们需要手写的错误输入，集中在一张无效输入表中，每行给出输入、所属格式与期望的具名错误。

## 断言

- 结构化输出用公开 Schema 严格解码后比较领域事实；错误按 `error` 代码断言，不按消息文本。
- 人读输出只在呈现测试中断言，规范化动态值（摘要、时间、路径前缀）后与期望文本比较。
- Use Case 验收表按行参数化，每行一个子测试，子测试名带行号（例如 C10）。
- 子进程断言失败时输出 exit code、signal、耗时与截断后的 stdout/stderr，见[共享资源与同步](testing.md#共享资源与同步)。
- 断言具体值，不断言「不为空」「大于零」这类任何实现都能满足的条件；集合按排序后的完整内容比较。

## 可追溯

测试与 Spec 的关系由测试标记拥有，`concord trace gaps` 从标记派生没有测试的 Use Case。本仓库的目标是零缺口：新增或修改 Use Case 的交付同时提交对应测试；尚未实现的 Use Case 留在缺口列表中，由一个打开的 Issue 跟踪实现，该 Issue 链接这个 Use Case 或其所属 Feature。自举测试检查每个缺口都有这样的 Issue，而不要求尚未实现的 Use Case 已有测试或实现关联。测试不指向 Roadmap、Design 或已删除的行为；行为删除时，对应测试在同一次交付中删除。

## 成本与稳定

| 指标 | 上限 |
| --- | --- |
| 完整门禁 | 参照机器空闲时单机不超过 5 分钟；CI 四个分片每片不超过 2 分钟 |
| 单个测试文件 | 不超过 60 秒 |
| 单个测试 | 所在层的 p50 上限 |

每次测试运行在 `.test-results/run-*` 中输出按耗时排序的测试文件与子进程启动次数。交付使某个文件超出上限时，把领域情形下移一层，或拆分文件以便并发，不提高上限。

不稳定的测试是缺陷：门禁不重试测试。空闲机器复跑通过的失败登记为 Issue，写明失败输出与运行时负载；修复时找到同步缺失或共享资源冲突，不以延长超时、重试整段操作或降低断言消除失败。

## 验收

- `concord trace gaps` 的缺口都有对应 Issue。
- 测试源码中除无效输入表外没有手写的受管格式文本。
- 最近一次完整门禁的耗时报告满足上表；超出项都有 Issue。
