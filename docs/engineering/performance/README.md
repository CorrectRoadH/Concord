# 性能测量

维护者用性能测量定位高频业务操作的成本，并比较优化前后的结果（[快到每次都愿意跑](../../taste.md#t-7)）。功能正确性由 Bun 测试验证，性能由 Bun 执行的 Mitata 场景测量。

预算数字由各 Feature 的 `performance.md` 拥有。运行方法见[测量命令](cli.md)，场景与预算的对应见[预算表与场景](format.md)，实现边界见[基准测试架构](architecture.md)。

## 性能约束

1. 场景直接调用真实业务入口，不复制算法，不用成功的空操作替代工作，不为性能跳过安全校验、来源校验或完整性检查。
2. 每项测量写清操作、输入规模、缓存状态和计时边界。函数耗时不代表 CLI 的整进程耗时，服务端操作耗时不代表用户界面完成时间。
3. 优化前后使用相同的方法与输入。改变测量边界时建立新的参照结果，不把不同边界的数字当成性能提升（[只声称证明过的](../../taste.md#t-5)）。

## 测量方法

- 运行时：使用 `.bun-version` 固定的 Bun，以及锁文件固定的 Mitata。
- 输入：使用场景声明的固定数据或私有临时仓库；来源提交或摘要与规模随测量结论记录。
- 边界：默认测进程内应用或领域操作，包括实际 I/O 与校验；准备 Fixture 与等待服务就绪不计入操作。
- 冷暖状态：场景明确应用缓存、投影、进程状态是否预先准备，不能把不同层的缓存统称为 cold。
- 采样：直接使用 Mitata 的预热、采样与统计，不自行规定固定七次采样、不剔除慢样本后重试。
- 环境：正式比较在同一机器、相同工具版本与输入下进行；测量期间不运行测试或其它已知重负载。
- 结果：使用 Mitata 官方报告与 JSON，不维护第二种采样记录格式。保存结论时写明具体场景与环境。
- 预算：只有边界、规模、状态与参照环境匹配的结果才可与 Feature 阈值比较。缺失结果不能通过预算验收。

CLI 启动成本只在需要分析该成本时单独测量，不是所有 Feature 的必测项。CLI 参数、输出与退出码继续由[测试分层](../testing/README.md#分层)中的功能测试验证。

## 失败判据

业务操作异常或资源清理失败使测量非零退出。工具成功退出只表示测量完成；预算由交付者对照原生报告判断，缺少结果、条件不匹配或超限均不能宣称预算通过。噪声较大的结果保留诊断，并在受控环境重测。

刷新上限是单次操作的墙钟约束，不由微基准的批次统计证明。其真实超时与资源生命周期由对应 Feature 验证，不借预算数字推断跨进程保证。

## 开发与交付流程

| 时机 | 操作 | 要求 |
| --- | --- | --- |
| 开发中 | 用 Bun 运行对应的 `bench/<feature-id>.bench.ts` | 查看实际操作的 Mitata 报告 |
| 交付前 | 运行受改动影响的场景；共享测量代码变化时运行 `bun run bench` | 完成采样与资源清理，核对适用预算 |
| 优化 | 在相同环境分别运行修改前后的相同场景 | 固定两边来源，保留完整报告，说明可比性 |
| 改变场景边界或数据规模 | 同时更新场景与 Feature 预算说明 | 重新建立参照测量，不能沿用不同边界的数字 |

benchmark 不进入 `bun run test` 的性能判定。`typecheck:scripts` 与 `lint` 检查场景及支持代码；预算与场景的对应在交付时审阅，不维护预算解析与自动裁决框架，也不重测 Mitata 的调度与统计实现。

性能结论与诊断保存在 Memory，原始报告留在工作目录外或忽略的诊断目录；不提交原始采样结果。定位热点使用 Bun CPU profiler，带 profiler 的运行不作为预算证据。
