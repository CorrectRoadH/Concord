# 性能测量

Concord 是 agent 高频调用的本地工具，性能是交付约束（[快到每次都愿意跑](../../taste.md#t-7)）。本文档包规定维护者怎样测量命令耗时、怎样判定通过，以及交付前要跑什么。

预算数字由各 Feature 的 `performance.md` 拥有，例如 [local SDLC 的性能预算](../../feature/local-sdlc/performance.md)。本文档包只拥有测量方法；Engineering 页面中的数字不是预算（[页面种类](../../document-model.md#页面种类)）。命令与记录格式见[测量命令](cli.md)，预算表与场景的写法见[预算表与场景](format.md)，脚本实现见[性能测量实现](architecture.md)。

## 性能约束

1. 高频公开操作必须具有由其 Feature 的 `performance.md` 声明的性能预算。超预算或缺少必需测量证据均不能判为通过。
2. 命令只读取完成目标所需的输入，不为只读操作加载无关子命令、启动无关进程或扫描无关 owner。所需输入包括安全、来源一致性及完整性验证所需的全部输入。
3. 优化前必须测量并定位瓶颈，优化后用同一方法复测；测量结果进入 Memory，预算进入 Feature，方法进入本文档包。不得为性能跳过摘要或 Schema 校验、路径安全、完整性门禁、授权检查，或缩减全局诊断范围。

## 测量方法

- 参照消费者：预算页声明的本仓库 commit 的独立 Git clone，冻结后测量。每组预算绑定该 commit、完整命令参数与参照环境。
- 参照环境：预算页声明的机器与 Bun 精确版本，使用构建到临时目录的归档。绝对预算只在参照环境判定，其它机器只做同机交错对照，判定回退比例。
- 测量记录：消费者 commit、纳入测量的来源及规模、基线与候选产物身份、Bun 精确版本及硬件信息。
- 基线：对照时的基线是 `--compare` 指定提交的构建产物，测量前确定，不在测后挑选。
- 对照消费者：两套产物各自使用同一冻结提交的独立 clone，因为一个项目目录同一时刻只有一个安装身份的工作区服务。两个 clone 各自初始化缓存与服务、分别预热并交错采样，比较结束时停止两边的服务。记录包含各消费者的路径、提交和缓存状态。
- 服务条件：默认按公开 CLI 的启动规则测量，查询预热会自动启动并复用工作区服务。场景声明 `server: running` 时，测量前显式启动该消费者的工作区服务并等待首份结果；预算行在测量内容中写明经由服务。
- 冷暖状态：warm 表示参照消费者已执行一次同一命令、HawDB 缓存有效；cold 表示执行 `concord cache clear` 后的首次运行。预算按 warm 判定，cold 只记录。
- 产物稳定：测量把被测归档构建到自己的临时目录，测量期间其它调用不能改写它。
- 计时边界：从启动安装目录中的 CLI 进程到进程退出的 wall time，stdout 与 stderr 重定向到文件。
- 采样：先预热一次，再对每条命令运行至少 7 次全新进程，取中位数（p50）。对照测量时新旧产物交错运行。
- 统计与阈值：p50 不超过所属 Feature 的预算，并且同机交错对照中 p50 相比基线的回退不超过 20%。
- 波动：同一命令的最大值超过 p50 的 2 倍、且超出 p50 不少于 20 ms 时，该组样本无效，须重新测量；连续两组无效视为失败。设 20 ms 下限，是因为 p50 只有几毫秒的场景中，个位或十几毫秒的离散是计时噪声。
- 进程上限：`## 刷新上限` 下的场景（例如后台刷新扫描）按最大值判定，在任何机器上超出都判失败，因为超时进程的结果不会被发布。

## 失败判据

超出预算或上限、回退超过 20%、样本无效或缺少必需测量证据，都不能判为通过。命令的输出、退出码与失败边界必须与优化前一致，不能以跳过校验换取时间。

测量结果、阶段分解与 profile 结论保存在 Memory；本文档包只声明方法与路径。Bun 源码测试不断言绝对耗时，`bun run gate` 只运行不计时的[覆盖检查与冒烟](format.md#覆盖规则)，不运行测量。

## 开发与交付流程

| 时机 | 命令 | 要求 |
| --- | --- | --- |
| 开发中 | `vp run bench --changed --quick` | 可随时运行，查看受影响场景的 p50 与预算的距离 |
| 交付前 | `vp run bench --changed --compare` | 改动选中任一场景时必须运行；全部判定通过才可交付 |
| 新增 Feature 的高频操作或新命令组 | 同一改动中增加预算行与场景 | 覆盖规则在 `bun run gate` 中强制 |
| 有意改变预算 | 修改 Feature `performance.md` 中的阈值，说明理由 | 附 `--compare` 记录，结论写入 Memory |

基线产物不具备的场景（例如新增服务条件或新命令）无法在基线上以同一条件测量；这些场景以 `--reference` 按候选的绝对预算验收，记录写明没有可执行基线，同一次交付中的其它场景照常 `--compare`。

交付前的 `--compare` 记录判定同机回退不超过 20%，不是参照环境上的绝对预算验收；绝对验收在参照环境以 `--reference` 执行。`--compare` 交错采样新旧产物，负载对两边相同，可以与门禁和其它开发同时运行；样本因负载波动而无效时重测该场景。`--reference` 判定绝对数值，与全量门禁一样占用本机全部门禁名额，运行期间本机不跑其它门禁。编辑照常进行。

回退或超预算时，先用 `bench:profile <场景 ID>` 定位，修复后用同一命令复测。记录的结论用 `concord memory add` 保存，不提交原始 JSON。

候选改变受管格式、基线产物无法解码同一冻结消费者时，同一消费者上的相对比较不成立。这次交付只按候选产物的绝对预算判定，交付说明与 Memory 记录断点提交。之后的交付以断点提交为基线，恢复相对比较。

基线不为此读取旧格式，也不改写冻结消费者（[当前格式](../../architecture.md#当前格式)）。

基线提交自身的缺陷使它的产物无法启动时（例如启动验证得到空的帮助输出），同样没有可执行的基线：这次交付按候选的绝对预算判定，交付说明写明基线提交、失败输出与原因，之后的交付以本次交付的提交为基线。不修补基线提交，也不在测后另挑一个能运行的提交。
