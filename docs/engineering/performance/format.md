# 预算表与场景

预算数字由 Feature 的 `performance.md` 拥有，场景由 `bench/<feature-id>.bench.ts` 拥有，两者用场景名关联，不另存预算登记表（[一件事只写一次，其余推导](../../taste.md#t-3)）。

## 预算表

`docs/feature/<feature-id>/performance.md` 的 `## 性能预算` 表声明可比较的操作耗时：

- 首列以行内代码列出一个或多个场景名，同一行共用阈值。
- 中间列说明业务操作、输入规模与计时边界。
- 末列为 `<整数>ms`，表头明确使用 Mitata 的 p50 统计。
- 同页声明参照环境、数据与缓存状态；不同边界的数值不能互相验收。

场景名使用 `<feature-id>/<名称>`，Feature 必须与预算页所属目录一致。README、Use Case 与 Engineering 页面链接预算页，不重复维护数字。

没有匹配的场景、没有可用统计或条件不一致时，不能判预算通过。纯函数、真实存储操作、HTTP 与 UI 事件的预算不能仅因单位相同就互相比较。

`## 刷新上限` 声明单次操作的墙钟约束，它与微基准统计分开。不能把 Mitata 批次归一化后的最大值当成一次真实刷新或进程超时证据。

## 基准场景

场景直接使用 Mitata 的 `bench`，名称与预算行对应。入口和运行方式见[基准测试架构](architecture.md#场景与入口)。不默认导出自定义描述对象，不再定义另一套场景字段或执行协议。

每个场景在源码旁写清输入、状态和计时边界。进程内操作经产品模块出口调用，I/O 使用真实适配；Fixture 负责建立状态，Mitata 负责采样。

只读操作可共享冻结输入。写入操作每次执行必须得到等价的起始状态；准备与重置的位置遵循 Mitata 的迭代语义，不能因工具批处理而让后续迭代测量空操作。

场景不带测试覆盖标记，不代替行为测试，也不证明 CLI 输出或跨进程生命周期。失败与资源清理规则见[Fixture 与生命周期](architecture.md#fixture-与生命周期)。

## 覆盖规则

性能场景按业务热点选择，不要求每个 CLI 顶层命令组有场景，也不维护命令豁免表。

门禁对所有场景源码做严格类型检查，交付审阅核对预算引用与场景名一致。场景必须调用产品实现；复用的 Fixture 按项目职责测试，不维护预算解析器，也不维护一套不计时的通用场景执行器。

删除业务操作时同步删除场景与预算。替换测量工具时保留产品行为测试，删除只验证已移除 runner、DSL、采样器与 reporter 的测试。
