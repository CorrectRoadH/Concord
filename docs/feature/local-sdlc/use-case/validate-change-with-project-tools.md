# 用项目自己的工具验证改动

## 用户目标

维护者把实现或修复交给 coding agent，要求它按项目约定运行测试并交付证据。Concord 帮助找到相关 Spec、实现和具体测试用例；执行命令与结果判断由项目与 agent 负责。

## 起始状态

- 项目的 `AGENTS.md`、Engineering 页或构建配置说明测试入口与环境准备方式。
- 改动有明确的 Spec 依据；需要延后处理的问题可以记录为 Issue，当场完成的小修复不要求建立 Issue。

## 完整路径

1. 确认行为与影响范围。 {#inspect}

   阅读相关 Spec，用 `concord trace show <Spec 路径> --fresh` 找到关联的实现和测试源码。需要具体测试身份时，用 `concord test discover` 收集用例、label 与来源位置，再查看标记绑定的原生用例。关联与收集均不证明测试执行、覆盖或通过。

2. 选择项目自己的验证方式。 {#select}

   agent 阅读项目指引和实际测试代码，选择能观察改动结果的最小测试范围。需要复现缺陷时先取得失败证据，再验证修复；不要求拆分提交、制造历史快照或冻结测试文件。

   项目已有测试框架与 CI 就是执行入口，不向 Concord 注册测试执行命令或结果报告协议。收集 adapter 只负责列出用例与元数据。没有自动测试入口时，agent 按项目要求执行适用的检查或人工验证，并说明证据局限。

3. 执行并检查结果。 {#run}

   agent 直接运行项目命令，负责环境准备、进程、超时、取消和清理。命令、执行范围、结果与未完成项写入交付说明；失败、未运行和全部跳过分别报告，不把退出码零或静态关联解释成行为覆盖。

   Concord 的 CLI、Web、RPC 和编辑器入口不派发测试体、不解析执行报告、不保存通过状态。服务只管理自己启动的收集与分析进程；服务停止、缓存清理和 Issue 关闭不接管 agent 的测试进程。

4. 核对关联并完成交付。 {#deliver}

   运行 `concord check` 检查文档和关联。它的成功与项目测试结果分别说明；检查不通过时修正本次改动引入的问题。

   已有 Issue 处理完后，运行 `concord issue close <id> --reason "处理结论"`。关闭只维护文件与引用，不运行或重复运行测试，不读取 CI 或 agent 的结果来决定能否删除。

## 结果

Spec、实现与测试关联一致，agent 提供实际验证证据，处理完的 Issue 被删除。测试结论由项目工具产出并由 agent 解释；Concord 没有测试通过凭证或修复认证状态。

## 边界与验收

| 情形 | 预期结果 |
| --- | --- |
| 项目使用任何测试框架，或没有测试工具 | 静态标记、查询、检查和 Issue 关闭均可使用；具体用例收集按 adapter 的能力提供，不要求执行适配 |
| 测试此前已执行 | agent 结合改动与项目规则判断是否重跑；关闭 Issue 不重复执行 |
| 收集到原生用例及 label | 按真实身份、范围或显式原生 ID 关联具体测试；缺少元数据时如实报告能力缺口，不执行测试补齐 |
| 标记存在、测试退役或测试文件未标记 | 展示作者声明与收集观察，不推断测试通过或覆盖率 |
| 请求运行测试或查看运行结果 | 指引交给 coding agent，附项目目录、Spec 与相关源码位置；不提供可执行测试任务或由 Concord 裁决的结果 |
| Issue 仍被其它文档引用 | 关闭按本地 Issue 的引用规则拒绝；是否跑过测试不影响这个判定 |
| agent 未执行验证或环境不可用 | 交付中明确未验证项，不能宣称测试通过；Concord 不代替 agent 执行 |

关联与收集由 Concord 提供，测试执行使用项目工具，遵循[用现成的能力，不重写](../../../taste.md#t-10)与[只声称证明过的](../../../taste.md#t-5)。
