# 工作区服务异常后恢复使用

## 用户目标

维护者在 Concord 更新或后台工作区服务失效（如卡在关闭阶段、子进程未释放或异常退出）后，继续打开原仓库运行命令或使用 mod，期望服务能自动拉起新实例、安全交接或明确报告阻断原因并自愈，不需要人工排障或误删私有状态。

## 起始状态

- 项目已经初始化。
- 仓库可能存在旧版本、已退出、卡在关闭阶段或异常退出遗留服务锁的工作区服务。

## 完整路径

1. 运行任意需要服务的命令或在 Herdr 中打开 mod。 {#detect}

   命令自动连接或启动工作区服务。若上一个服务已经退出且服务锁已释放，命令自动启动新实例，原查询正常返回。

2. 服务需要替换时完成安全交接。 {#replace}

   安装包更新后，直接运行 `concord list feature`，不需要先执行 `server stop`。即使协议相同，安装身份不同也触发替换：等待旧实例退出并确认服务锁与自有资源释放后，启动当前安装的实例，再执行本次查询。

   用 `concord server status` 核对新实例的 token 与安装身份。上述结果为预期行为；具体交接和并发边界见[启动与裁决](../architecture.md#启动与裁决)。

3. 服务卡在关闭阶段时报告确切阻断原因。 {#blocked}

   运行记录处于 `stopping` 或 socket 无法握手、但服务锁仍被存活进程占用时，启动者不把握手失败等同于服务不存在，不盲目启动新实例争锁。确认退出超时后报告具体的未完成清理阶段与持有者信息。

4. 异常解除后自动恢复使用。 {#resume}

   阻断进程退出或锁释放后，下一次命令或 mod 轮询自动重新拉起服务并完成查询；mod 错误横幅自动收起并恢复正文，只有确实未初始化的仓库才显示初始化入口。

## 结果

| 情形 | 结果 |
| --- | --- |
| 服务已经退出 | 下一次命令自动启动新实例，原查询正常完成 |
| 安装包更新，协议相同 | 自动停止不同安装身份的实例，以当前安装启动后执行原命令 |
| 协议不同 | 按同一交接流程替换，不能绕过清理确认 |
| 同一安装并发查询 | 只保留一个胜出的服务，其余命令复用它 |
| 不同安装竞争 | 本次命令至多发起一次替换，再次不匹配返回 `WorkspaceServerBusy` |
| 查询服务状态 | 只观察，不因安装不匹配而停止或启动服务 |
| 在途写入结果未知 | 保留恢复材料，不自动重放该写入 |
| 服务卡在关闭阶段 | 保持阻断状态，报告具体未完成的清理阶段与持有者 PID，不发起冗余争锁 |
| 持锁进程已死（孤儿锁） | 确认进程不存在后清理陈旧记录与 socket，重新取得服务锁并启动 |
| 恢复成功 | 原查询成功，mod 自动恢复；只有确实未初始化才显示初始化入口 |
