# 工作区服务的运行形态

## Problem

[工作区服务](../../feature/local-data-engine/architecture.md#工作区服务)当前规定三种进程：主进程持有服务锁、持久库、socket 与 HTTP；长期计算进程执行刷新与只读查询；每个 Web 写入、恢复或测试终结另起一个操作进程。工作区导航来自 `workspace_projection` 命名空间中的单行结构快照（最多 8 MiB），每个代次整行替换。客户端分两套协议：面板与 CLI 经 `unstable/rpc`，Web 经 HTTP 与 SSE，定向读取分别是 RPC `read` 与 `/api/file`，两者以文字约定「相同」。

需要决定：服务内部需要几个进程、服务持有什么状态、不同客户端怎样共用一份操作定义，以及怎样确定地测试服务的计时与状态。

## 证据

2026-10-30 在参照机器（16 核，Linux x64）上对本仓库运行 P1 末尾构建（f4bd3ce）的 `concord --json trace check`，墙钟 2.9 s，CPU profile 2.77 s：

| 成本 | ms |
| --- | ---: |
| HawDB `Database.scan`（整个命名空间读出、解压与解码） | 704 |
| HawDB 打开与原生产物校验 | 143 |
| Markdown 解析（micromark、mdast） | 约 350 |
| 路径安全 `lstat` | 137 |
| Schema 解码 | 约 150 |
| 模块编译与加载 | 约 150 |
| 读文件与 sha256 | 约 60 |

[CLI 热路径](../cli-hot-path/README.md)的剖析同样测得读取全部 934 个来源并计算 sha256 约 14 ms。读取与摘要不是主要成本；主要成本是每个进程重新打开并扫描持久库、重新解析文档。常驻进程在内存中保持解析结果即可去掉这两项，不需要让查询跳过来源核验。

服务内部的计算进程与操作进程是为两件事设置的：同步的解析与 trace 会阻塞事件循环，使握手、推送与 HTTP 停顿；失控的计算需要能被强制终止。Node 的 worker thread 同时满足两点（独立事件循环，`terminate()` 强制结束），且不需要进程组清理、IPC 序列化边界与每次写入几百毫秒的 Node 启动。

## 方案

### 一个进程，两个线程

服务是一个 Node 进程：

| 线程 | 职责 | 不做 |
| --- | --- | --- |
| 主线程 | 服务锁、运行记录、socket 与 HTTP 监听、订阅与推送、来源监听、持久库句柄、计时与状态机、操作调度 | 解析、trace 与领域计算 |
| 计算线程（一个 worker thread） | 刷新、白名单查询、Web 写入的规划与发布、恢复、测试终结；持有内存解析缓存与当前代次的结构 | 持久库、socket、HTTP |

计算线程按到达顺序处理请求，写入与查询优先于刷新；刷新在文件边界检查中断。一个请求超过 60 秒或线程崩溃时，主线程 `terminate()` 计算线程，在途请求以具名错误失败，新线程冷启动。外部 runner 与 Git 仍经 `OwnedProcess` 启动子进程，这是唯一的子进程。

持久库只在主线程打开。启动时主线程从持久解析命名空间读出已有条目交给计算线程，计算线程产生的新解析结果交回主线程批量写入。

### 服务持有的状态

- 计算线程按 `(路径, 内容摘要, 解析器身份)` 在内存中保持解析结果，每个代次保持一份结构（条目、关系、诊断、概念目录）及其 trace 编译结果。
- 代次是递增编号加该结构，只在内存中存在。服务重启后先用持久解析缓存重建结构，再发布第一个代次。取消 `workspace_projection` 命名空间与 8 MiB 单行快照。
- 查询与刷新每次都读取当前来源并核对摘要、目录集合、配置、路径安全、`publication.revision` 与恢复状态，规则与本进程计算相同；摘要命中的文件直接用内存中的解析结果，输入摘要全部相同的 trace 直接复用。经由服务的结果与本进程计算的结果相同。

### 一张操作表

服务的每个操作（`hello`、`subscribe`、`read`、`query`、`http`、`cache-clear`、`feedback-merge`，以及 Web 的写入、恢复与测试任务）只定义一次：输入 Schema、结果 Schema、具名错误与准入额度。RPC 与 HTTP 都是这张表的适配层，SSE 是 `subscribe` 的另一种编码；`/api/file` 与 RPC `read` 调用同一个操作。HTTP 适配层另外负责 Host/Origin 校验与 JSON 编码，RPC 适配层负责二进制序列化与帧准入。

### 计时与测试

服务的计时（握手 1 秒、交接 3 秒、worktree 消失 5 秒、锁核对 5 秒、计算 60 秒、空闲 10 分钟、监听合并 250 毫秒与 2 秒）全部经 Effect `Clock` 与 `Schedule` 表达。服务由 Layer 组成，测试在测试进程内构建同一 Layer，以 TestClock 推进时间，以真实 socket 与真实临时 Git 仓库验证状态机、订阅、退出与清理。计算执行器有两个实现：worker thread 与当前线程；`view --in-process` 与进程内测试使用当前线程实现，产品服务使用 worker thread。进程层只测试跨进程才存在的行为：服务锁争用、进程被杀后锁释放、CLI 与面板拉起服务、不同安装身份的交接。

### 性能判定

Feature 页的预算行默认在没有工作区服务时测量。经由服务的命令另设场景，场景声明 `server: running`，预算行写明该条件。

## 待审问题

1. 单个计算线程同时承担刷新、查询与写入，写入优先与刷新中断是否足以保证 Web 保存与 CLI 查询的延迟；是否需要第二个线程。
2. 取消持久的工作区代次后，服务重启到第一个代次的时间（持久解析缓存 + 结构重建）能否满足面板首屏要求。
3. 写入在计算线程中执行时，publication lease、journal 与恢复的崩溃语义是否与独立操作进程相同：线程被 `terminate()` 时持有的 lease 与 journal 由谁回收。
4. 一张操作表能否覆盖 Web 现有的全部 HTTP 路由（包括 p5 编译、Git 视图与预览导出），哪些路由不属于工作区服务。
5. 当前线程执行器作为第二个实现，是否构成为测试而设的双轨。
