# CLI 热路径与 HawDB 进程模型

## Decision

Undecided.

## Rationale

待独立复审与原生维护实测后裁决。当前比较：per-command-open 不满足 [L5](LIMITS.md#l5-按引擎规定持有-hawdb)。它让许多短命进程轮流打开一个按引擎规定只能由一个进程持有的目录，引擎后台维护无法运行，并发命令只能互相竞争并回源，因此 [G5](GOALS.md#g5-并发调用互不串行) 不满足。它也只能部分满足 [G1](GOALS.md#g1-启动在-50-ms-以内)：spike-startup 实测，完全打包后真实命令进入命令逻辑前仍约 139 ms。

hawdb-owner-service 以一个共享的后台进程满足引擎规定，并让 CLI 成为只转发参数的薄客户端。两者都保留现行的来源读取与摘要核验，不修订宪法。剩余待验证项是引擎维护的实际效果、版本交接、进程内回退，以及命令迁移到调用上下文服务后与独立进程输出的一致性。

## Rejected Options

待裁决。

## Residual Risks

hawdb-owner-service 在定案前还需补齐以下规定，每项都要可执行、可验收：

- 逻辑会话：`openHawdb` 的 readOnly、create 与 close 语义，会话绑定所有者实例与数据库代次，clear 与交接使旧会话失效；dry-run 不连接后台。
- 启动与清理：每个所有者身份只有一个监听者的排他启动协议；只在证明无活实例时删除陈旧 socket 与记录；运行目录的类型、属主、权限与路径长度检查。
- 状态机：每个缓存根的 Opening、Owned、Draining、Closed、Clearing、HandingOff 状态；clear 与 release 不持原生锁等待 publication，取不到协调时延期并回源。
- 资源预算：全局与每个 worktree 的打开库数、内存、线程、连接、排队与在途字节；未引用的库按策略关闭；测试运行只回收自己的库。
- 逻辑淘汰：引擎负责物理维护，命名空间与总逻辑预算仍由 Concord 约束；维护是有预算的串行作业，错误分为延期、超限、损坏与安全失败。
- 同步桥：每次调用有截止时间与请求代次，worker 失败时一定唤醒主线程；输入、输出与队列分别限额；写请求断线视为结果未知，不重放。
- 命令执行（原第 3 阶段）：执行器身份绑定完整安装身份与 Node 运行时；全局状态通过每请求的调用上下文与 Scope 隔离。218 处全局 `process` 用法与若干模块级单例需逐一处理；先声明可托管的命令白名单，长服务、交互入口与外部 runner 保留独立进程；取消、流与结果未知状态单独定义。
- 检索（原第 4 阶段）：引擎全文索引与现行逐词子串匹配的命中集合、排序与就绪语义需单独定义，不能默认等价。

另：spike 实测（提交 `refs/spikes/reclaim`）表明，启用 background-maintenance 并长期持有句柄时，引擎约 60 秒完成自动 checkpoint。但 150 秒内它不回收旧根页与不可达对象；2000 次写入后长期持有组为 90.55 MiB，而关闭时显式 reclaim 的组为 22.21 MiB。长期持有因此不能解决缓存膨胀，物理上限由 Spec 中的回收与丢弃重建保证。另一个进程连只读打开都会失败，所以共享后台的收益只剩并发与启动两项。

持久解析投影在每个命令各自打开数据库时是净损失：实现后缓存从 8 MB 增至 80 MB，`docs check` 慢 46%、`memory index` 慢 72%，打开持久库的成本超过省下的解析时间。它只在库被长期持有时才可能有收益，因此不作为两个候选的共有改动，归入 hawdb-owner-service 的范围，在其定案后实测。
