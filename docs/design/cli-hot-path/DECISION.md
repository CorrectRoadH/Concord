# CLI 热路径与 HawDB 进程模型

## Decision

Selected: [workspace-server](plans/workspace-server/README.md)

## Rationale

HawDB 规定一个目录由一个进程长期持有。workspace-server 让每个 worktree 唯一的工作区服务持有缓存，其它进程只取领域结果或改用内存缓存，因此满足 L5，也不需要远程数据库句柄、同步调用桥或在后台执行任意命令。Herdr 面板与 Web 需要的实时推送由同一个进程提供。候选表中的「满足」表示方案机制满足约束，不代表实现验收通过。

G1: 静态版本与帮助已达成；其余命令经由服务查询时，CLI 只加载协议与格式化代码，是否进入 50 ms 由第 2 阶段实测判定。

G2: 服务运行时命令免去打开库与解析，只付出读取与摘要；服务未运行时与现状相同。

G3: 解析结果在服务的内存命名空间中按路径与摘要命中，只有变化的来源重新解析。

G4: 物理体积仍由现行两级维护保证，服务在空闲时执行；spike 表明长期持有本身不回收空间。

G5: 服务运行时当前版本的其它进程不再打开该目录；持久库被占用时可重建的解析缓存降为内存缓存，因此即使没有服务，并发命令也不因 `HawdbBusy` 失败，诊断仍保留占用原因。

G6: 门禁中的临时仓库不启动服务，本方案只通过 G1 的静态部分降低单次调用成本；门禁时长另由工程机制解决。

G7: 解析结果完全放在 HawDB 内存命名空间，不另建持久投影；物理维护的时机仍由 Concord 编排，检索不在本设计范围。

G8: 一个进程监听、刷新并推送代次，面板与 Web 只订阅，首屏读取已发布代次。

## Rejected Options

hawdb-owner-service 按当时的写法以每个用户一个后台托管全部 worktree 的数据库，并分阶段在后台执行任意命令，第二轮独立审查列出的远程句柄、同步桥、跨 worktree 资源与命令隔离问题都来自这一写法。per-command-open 顺序打开同一目录并不违反引擎的单进程互斥，但每个命令都要重新打开持久库、读取并解码解析投影，缺少长期进程的热态，也没有实时推送。持久缓存被占用时降为内存解析缓存是两种结构都能采用的独立改动。

## Residual Risks

本裁决依据用户 2026-10-30 的指示作出；独立审查在六轮复核后通过，修订已提升进现行 Spec。服务锁需要原生绑定新增入口；Herdr 插件上下文能否提供当前 pane 的工作目录、manifest 的 split 方向尚未核实；面板的终端渲染依赖尚未选定。第 2 阶段经由服务的查询能否让 G1 达标待实测。
