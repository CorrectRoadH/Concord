# CLI 热路径与 HawDB 进程模型

所有数值在[性能验收](../../engineering/concord-self-hosting/performance.md)规定的参照环境与方法下按 warm p50 判定，参照消费者为预算表声明的本仓库 commit 的独立 clone。

## G1: 启动在 50 ms 以内

`concord --version`、`concord --help` 从进程启动到退出 p50 ≤ 50 ms（同环境空 `node -e 0` 约 30 ms）。任意子命令从进程启动到其命令逻辑开始执行的固定开销 ≤ 50 ms，模块加载计入固定开销。来源：用户要求；Problem 一节实测 310 ms。

## G2: 缓存已热的只读命令为百毫秒级

来源未变、缓存已热时：`concord memory index` 与各类 `list` ≤ 100 ms，`concord docs check` ≤ 150 ms，`concord trace gaps` ≤ 150 ms，`concord check` ≤ 250 ms，`concord doctor` ≤ 250 ms。耗时随来源文件数线性增长，每千个未变文件的增量 ≤ 25 ms（含读取与摘要，参照实测约 14 ms）。来源：Problem 一节实测 0.4–5.4 s。

## G3: 少量变更只付出变更文件的成本

修改、新增或删除 k 个来源文件后，下一次只读命令相对 G2 的增量中，解析部分与 k 成正比；读取与摘要仍覆盖全部来源，按 G2 的线性成本计。

## G4: 缓存体积与打开耗时不随使用时间增长

持续写入 10000 个缓存代次后，物理缓存体积 ≤ 逻辑持久预算的 2 倍加 32 MiB，持久库打开 p50 ≤ 60 ms。已膨胀的现有缓存在首次可写使用后回到该范围。来源：Problem 一节实测 466 MB、打开 1118 ms。

## G5: 并发调用互不串行

同一 worktree 内多个只读命令并发运行时，各自耗时相对单独运行的增长 ≤ 50%，不因缓存锁或租约排队。

## G6: 支撑分钟级交付门禁

G1–G3 合计使测试中的单次 CLI 调用成本降低一个数量级以上，使本仓库完整门禁有条件在参照机器上降到 2 分钟内。门禁本身的时长由工程机制验收，本 Goal 只判定单次调用成本。

## G7: 引擎能力不在外部重写

缓存的维护（compaction、旧代次回收）与 Memory、Issue 检索由 HawDB 自身完成，Concord 不另行实现淘汰顺序、代次重建或检索评分。判据：上述职责在 Concord 源码中没有对应实现，验收以 C7 与 C17 为准。来源：Problem 一节的根因。
