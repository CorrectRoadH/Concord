# 以 Spec 驱动开发的核心模型

| Case ID | User Problem | Fixed Input | Acceptance Result |
|---|---|---|---|
| C1 | 新增一项能力 | 维护者写一个 Feature 与两个 Use Case | 无需配置或专用命令；`check` 通过；`trace gaps` 列出两个尚无测试的 Use Case |
| C2 | 修改已有行为 | 改写一个 Use Case 的验收 | 只改该文件；指向它的测试在 trace 中可见 |
| C3 | 有两个可行设计 | 比较候选并裁决 | 裁决记录不随实现改写；采用的规则写进 architecture 页 |
| C4 | 修复一个缺陷 | 观察到错误行为，写测试，修复 | 缺陷有唯一的跟踪位置；新 clone 上也能复现「修复前失败、修复后通过」 |
| C5 | 记下一条经验 | 排障后得到根因与做法 | 经验有唯一位置，可被检索，链接到相关 Spec |
| C6 | 记录尚未实现的方向 | 一个已想清楚但暂不做的能力 | 有唯一表达方式，不被误认为已交付 |
| C7 | 只改内部实现 | 重构，不改行为 | 只改 architecture 页与代码 |
| C8 | agent 开始新会话 | 读取当前约定 | 一条命令列出当前 Spec、未完成的工作项与相关知识 |
| C9 | 重命名一个 Feature | 移动目录 | 不需要修改文件内的元数据；指向旧路径的链接由检查报告 |
