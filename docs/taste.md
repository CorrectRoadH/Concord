# Concord 的品味

品味是这个项目判断“什么是好的”的共同标准：规则写不到的地方按品味选择，审阅时按品味判断好坏，可以链接某条品味指出变化哪里不合品味。产品必须满足的行为写在 Feature，仓库自身的工程规则写在[工程页](engineering/self-hosting/README.md)，页面职责由[文档模型](document-model.md)拥有。

## 总则 {#general}

1. 品味说明它解决什么问题、好的样子和坏的样子。它是判断标准，不是逐条检查的规则；品味之间需要取舍时，在变化说明或 Memory 中写明理由。 {#general-taste}
2. 品味不写达成它的机制。实现方式写在所属 Feature 的 architecture 页，产品行为写在行为页，仓库维护机制写在工程页。 {#general-rules-only}
3. 用现行句式，不描述与过去的差别。 {#general-present}
4. 依据某条品味的句子旁写指向其 ID 的链接，不用“第 N 款”这类序号文字。ID 一经采用不改名、不复用；修订后检查链接被修改 ID 的页面。 {#general-link}
5. 本文件可以直接编辑，修改历史由 Git 保存。新发现的跨功能偏好写进这里，功能专属细节留在对应 Spec。 {#general-amend}

## T-1 读得懂胜过写得全 {#t-1}

Spec 没人看得懂，就没人认真审阅，也就没人维护。

- 好的样子：README 像使用教程，先讲能做什么，再给一个照着就能运行的例子；不同用户目标或处理路径各有一个 Use Case，同一路径的输入变化与错误结果用表格说明；多方协作与状态变化配一张 p5 动画。
- 坏的样子：README 开头就是字段、退出码和边界条件；用一串子规则枚举各种情形。

## T-2 一个词一个意思 {#t-2}

人和 AI 用不同的词说同一件事，或用同一个词说两件事，读者只能猜。

- 好的样子：领域名词先在 `concepts.md` 定义再使用；改名时留下旧写法；命令、字段和错误码写在行内代码里；一个页面只用项目文档的主语言。
- 坏的样子：快照与 snapshot 混用；“发布”同时指写入的提交和软件发版；页面在中英文之间切换。

## T-3 一件事只写一次，其余推导 {#t-3}

同一事实的多份副本迟早不一致，手工维护的登记表总会过期。

- 好的样子：每项事实只有一个 owner，其它页面链接它；反向关系、索引和汇总从来源推导；缓存随时可以删除，删除后结论不变。
- 坏的样子：手工 INDEX；第二份关系清单；同一个错误码在两个页面各定义一遍。

## T-4 写现在，不写过去 {#t-4}

历史叙述让人和 agent 把旧规则当成现行规则，兼容层让系统同时存在两套真相。

- 好的样子：Spec 只声明当前行为；排障经过、进度和交接写进 Memory；格式变化时直接改写文件。
- 坏的样子：“目前”“已改为”“旧版本”；迁移说明；为旧格式保留的读取路径。

## T-5 只声称证明过的 {#t-5}

没有证据的“已修复”“已覆盖”，会让人放心地出错。

- 好的样子：修复在缺陷提交和修复提交上各验证一次，结论写明证明了什么、没有证明什么；标记表示关联，不表示覆盖。
- 坏的样子：“check 通过，所以功能完成”；用一次运行代表所有情形。

## T-6 文件是界面，命令只是助手 {#t-6}

只能通过工具修改的状态不透明，也把使用者锁在工具里。

- 好的样子：全部内容是 Git 中的普通文件，人和 agent 直接编辑；命令只执行必须运行的步骤，并把结果写回文件；门禁判断变化是否合法。
- 坏的样子：必须经过某个命令才能修改的状态；只存在于数据库里的事实。

## T-7 快到每次都愿意跑 {#t-7}

慢的检查会被跳过，被跳过的检查等于没有。

- 好的样子：高频命令有性能预算；先测量、定位瓶颈再优化；命令只读取完成目标所需的输入；查询读服务持续维护的缓存，只核对上次以来变化的部分，结果仍是当前的。
- 坏的样子：为了更快跳过校验；没有测量就改实现；服务开着，每次查询仍重新读取与核对全部来源。

## T-8 规则少而硬，机制留给实现 {#t-8}

规则越长越没人读；把机制写进规则，改实现就得修规则。

- 好的样子：每条品味一句话，配好坏对照；产品规则写在 Feature，机制写在 architecture 页。
- 坏的样子：在品味里写句柄、租约、Schema 版本和注释前缀。

## T-9 适配项目的开发方式 {#t-9}

Concord 围绕使用者选定的项目目录工作，分支与 worktree 的用法由项目决定。

- 好的样子：在 main 上开发、切换分支或使用多个 worktree，都使用同一套命令；运行状态随项目目录隔离。
- 坏的样子：要求用户先创建特定分支或 worktree，才能采用 Concord 的开发流程。

## T-10 用现成的能力，不重写 {#t-10}

自己写的任务调度、进程池和文件包装要一直维护，而且总比官方实现少考虑一些情形。

- 好的样子：先查 Vite+、Effect、Node 和测试工具是否已经提供，直接配置使用；自写代码只承担项目特有的规则，并说明现成能力缺了什么。
- 坏的样子：手写测试发现、分片、进程池和 reporter；为一个已有 API 再包一层同名函数；保留没有调用者的脚本。

## T-11 Spec 写到实现者不用再问 {#t-11}

实现者要靠猜补全的 Spec，会被各自猜成不同的样子，验收时也没有标准可依。

- 好的样子：写 Spec 的人定下命名、行为、边界和验收方式；实现者照着做，只在 Spec 缺失或与事实冲突时停下，带着证据回到 Spec；验收者按 Spec 和实际运行判断，不按实现者的自述判断。
- 坏的样子：只给功能标题就开工；实现者自行决定公共命名或错误语义；用“测试通过”代替对照 Spec 的验收。

## T-12 Spec 随时可改 {#t-12}

Concord 先改 Spec 再实现，实现进行中 Spec 仍会变。等实现告一段落再改，实现者就照着过期的规则继续写；为改 Spec 冻结仓库，并行的人就得停下来等。

- 好的样子：Spec 随时直接改；受影响的实现者重读改动的页面，按最新 Spec 调整已经写好的部分；检查只回答它读到的文件，结果过时就重跑。
- 坏的样子：为了让门禁或测量跑完而冻结 docs；把 Spec 修改攒到“空闲窗口”再写；按开工时的旧 Spec 交付并声称完成。
