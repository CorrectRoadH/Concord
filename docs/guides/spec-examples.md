# Spec 写作示例

下面是虚构阅读产品的文档成稿，展示怎样从用户目标写出 README、Use Case 和必要的细节页。路径是示例中的目标位置；围栏内的 Markdown 可以单独保存为对应文件。所有交互结果均为预期结果，不是任何实际产品的运行证据。

## 目录树：先看文档怎样组织

这是阅读产品按内容需要组织的目录，不是必须全部生成的文件清单。init 提供基础布局；每个具体文档包必需 README，其余页面有对应内容时才创建。

```text
docs/
├── README.md                         # 项目用途与阅读入口
├── concord.md                        # init 生成的 Concord 使用指引
├── taste.md                          # 跨功能的判断标准
├── concepts.md                       # 全局领域名词

│   │   ├── ui.md                      # 阅读界面的状态与操作
│   │   └── architecture.md            # 阅读位置的实现职责与生命周期
```

分类目录中 init 生成的其它 README 在图中省略。Use Case 的入口 `use-case/README.md` 按需添加；局部术语放所属目录的 `concepts.md`。能力只有界面入口时，不补 CLI 或 API 空页；数据结构简单时可以只在 architecture 页说明。

Feature 表示已采用的产品目标，目录位置不证明代码完成。Roadmap 表示尚未采用的方向；Design 只保存未决取舍。正文示例从树中的 `reading/` 展开，展示这几页如何互相链接。

## Feature README：从主要使用者开始

目标位置：`docs/feature/reading/README.md`。

```markdown
# 阅读书籍

读者在浏览器中打开书籍、翻页，并在下次打开时继续上次的阅读位置。

## 你可以做什么

- 从书库打开一本书，通过上一页、下一页或页码输入框翻页。
- 关闭书籍后再次打开，继续阅读上次保存的页码。

## 上手

以下为预期结果。

1. 登录后打开“书库”，点击《植物观察》的封面。
   阅读页面显示正文和页码；首次打开时显示第 1 页。
2. 在页码框输入 `12` 并确认。
   正文切换到第 12 页，页码框显示 `12`。
3. 看到“位置已保存”后返回书库，再次打开这本书。
   正文直接显示第 12 页。

## 怎样工作

阅读位置按账号和书籍保存。同一本书在不同账号下的阅读位置互不影响。

## 范围与验收

本功能负责打开书籍、翻页和恢复阅读位置。书籍上传由书库功能负责。
按上手步骤重新打开书籍后仍显示第 12 页，即满足这条路径的预期结果。

## 用户路径与细节

- [继续上次阅读](use-case/resume-reading.md)
- [阅读界面](ui.md)
- [位置保存的实现](architecture.md)
```

这里的上手沿着读者的入口走。运维人员生成文字层、管理员配置存储是另外的目标，不能因为有可复制的命令就拿来替代读者上手。

## Use Case：一条能走完的用户路径

目标位置：`docs/feature/reading/use-case/resume-reading.md`。

```markdown
# 继续上次阅读

## 用户目标

读者关闭书籍后再次打开，希望从上次保存的位置继续阅读。

## 起始状态

- 读者已登录，书库里有一本可阅读的书。
- 这本书至少有 12 页。

## 完整路径

以下为预期结果。

1. 在书库点击书籍封面，看到正文与页码框。 {#open-book}
2. 在页码框输入 `12` 并确认，正文显示第 12 页；等待界面显示“位置已保存”。 {#save-position}
3. 返回书库，再次打开同一本书，正文与页码框均显示第 12 页。 {#resume-position}

## 结果

再次打开后可以继续阅读第 12 页，无需手动重新定位。

| 情形 | 读者看到什么、接下来怎么办 |
| --- | --- |
| 保存位置失败 | 正文仍可阅读，显示“位置未保存”和“重试”；重试成功后显示“位置已保存” |
| 读取已保存的位置失败 | 显示“无法恢复阅读位置”和“重试”；不把第 1 页当作成功恢复并覆盖原位置 |
| 切换到另一个账号 | 按新账号的阅读位置打开，不显示原账号的保存结果 |

## Spec 来源

- [阅读书籍](../README.md)
- [阅读界面的状态与操作](../ui.md)
```

“打开书 → 翻页 → 保存 → 重新打开”推进同一个目标。“向 AI 提问 → 管理员充值 → 查账单”则拼接了独立目标，应分别写成提问、调整积分、查看账单的路径。删除书籍也不是上传成功后的必经步骤。

Use Case 的步骤写用户动作与观察结果。请求头、SQL、组件回调和锁的变化属于实现说明，不能替代用户操作。

## 细节页：界面与实现各回答自己的问题

目标位置：`docs/feature/reading/ui.md`。

```markdown
# 阅读界面

正文占据主区域，页码输入框与上一页、下一页按钮位于底部工具栏。页码框支持键盘聚焦，按 Enter 确认跳转。

## 位置保存状态

状态提示位于页码框旁，通过可访问的状态区域播报；不用颜色作为唯一提示。

| 状态 | 呈现与操作 |
| --- | --- |
| 正在保存 | 显示“正在保存位置”，允许继续阅读 |
| 保存成功 | 显示“位置已保存” |
| 保存失败 | 显示“位置未保存”和可用键盘操作的“重试”按钮 |

## 视觉验收

在窄屏上，状态提示与翻页按钮不遮住正文；保存失败时，读者能找到重试入口。完整操作与结果见[继续上次阅读](use-case/resume-reading.md)。
```

目标位置：`docs/feature/reading/architecture.md`。

```markdown
# 阅读位置的实现

## 职责

阅读界面拥有当前页码和保存状态；位置服务按账号与书籍保存页码。使用者可见的失败与恢复规则由[继续上次阅读](use-case/resume-reading.md)拥有。

## 请求生命周期

打开书籍时，先读取该账号的保存位置，再设置初始页码。读取失败不触发位置写入。

每次翻页保存都绑定发起时的账号、书籍和请求序号。连续翻页时按发起顺序提交；旧请求的完成不能把界面改回旧页码。

关闭书籍或切换账号时，取消尚未发出的保存请求，并忽略旧请求返回的界面更新。服务端始终按请求所属的认证账号写入。
```

实现段落解释职责和生命周期；它不在 Use Case 中重复出现。详细存储结构需要时写入 data-model 页。普通读者不调用网络协议时，无需为了凑齐页面而创建公开 API 文档。

## CLI 用法：只有实际入口是命令时才写命令

虚构导出工具的一条 Use Case 可以这样写。`shelf` 仅用于示范，不能直接复制成接入项目的命令。

```markdown
# 导出阅读记录

## 用户目标

读者希望把阅读记录交给电子表格工具分析。

## 起始状态

本地已安装并配置 `shelf`，账号有阅读记录，目标文件 `reading.csv` 不存在。

## 完整路径

以下为预期结果。

1. 在终端执行 `shelf export --output reading.csv`，看到 `Exported reading.csv`，命令退出码为 `0`。 {#export}
2. 用电子表格工具打开文件，确认标题行包含书名和阅读日期，内容包含账号的阅读记录。 {#inspect}

## 结果

读者取得可供后续分析的文件。若目标文件已存在，命令以退出码 `1` 报告 `OutputExists`，保留原文件；读者换一个文件名后重试。
```

命令页定义全部参数与错误，文件格式页定义 CSV 字段；Use Case 展示如何组合工具达到目标。已有命令的输出应来自隔离环境的实际运行，未验证的例子保留预期标注。

## 性能：沿用接入项目的技术栈与指标

下面是另一个虚构项目：已有 Go 搜索服务和 Go benchmark，只补性能声明。目录可以这样安排；这些路径、命令和预算是写法示例，不是对接入项目的要求。

```text
docs/
├── feature/search/
│   ├── README.md
│   └── performance.md
└── engineering/measurement/
    └── README.md
internal/search/search_test.go
```

`docs/feature/search/performance.md`：

```markdown
# 搜索性能

以下是目标预算，尚未测量。测量方法由[搜索基准](../../engineering/measurement/README.md)拥有。

## 条件与预算

参考环境为 Linux amd64、专用 2 核 CPU、4 GiB 内存，使用项目锁定的 Go 版本。索引在计时前加载完毕，包含固定的 10 万条记录；查询集、结果数量与排序方式固定。

| 操作 | 测量边界 | 指标与预算 |
| --- | --- | --- |
| 单次关键词查询 | 从调用搜索函数到取得前 20 个结果；不含 HTTP、索引加载与磁盘读取 | 每轮平均耗时不超过 200000 ns/op，平均分配不超过 4096 B/op |

这个预算约束常驻索引的查询成本，不声明 HTTP 尾延迟。冷启动与网络请求需要各自的场景和观察入口，不能用本场景的结果证明。
```

`docs/engineering/measurement/README.md`：

```markdown
# 搜索基准

维护者用项目已有的 Go benchmark 检查[搜索预算](../../feature/search/performance.md)。基准实现在 `internal/search/search_test.go` 的 `BenchmarkSearch`，不引入另一种语言或工具。

## 运行与判断

从项目根目录执行 `GOMAXPROCS=1 go test ./internal/search -run '^$' -bench '^BenchmarkSearch$' -benchmem -count=5`。这是预期用法，须以该项目实际实现核对。

基准在计时前构造独立的临时索引，加载固定数据；计时循环只调用被测函数，结束后释放索引并删除临时文件。正常退出和失败退出都执行清理。

检查五轮输出的 ns/op 与 B/op 是否各自满足预算，并保留环境、命令与原始输出。若数据集改变、初始化被计入或宿主同时运行其它重负载，结果不能与该预算比较。缺少某轮或基准未被匹配时不算通过。

每轮的 ns/op 是该轮的平均成本，不是单次查询的 p95 或 p99；尾延迟必须用相应请求测量方法验证。
```

性能页拥有操作与预算，Engineering 拥有运行方法，测试文件拥有可执行定义。预算没有理由要求所有接入项目都采用 Concord 自身的工具、统计口径或目录。

## 品味与测试关联也要对应真实含义

品味可以写“失败应让使用者看见并能恢复”，解释静默丢失阅读位置为什么不好。“冻结请求序号并取消旧请求”则是架构中的实现机制。

审阅正文时，检查主要使用者能否照着上手、路径是否服务同一个目标、细节是否放在正确页面。正文和路径稳定后再关联实现与测试：位置服务的隔离测试关联隔离保证，界面恢复测试关联恢复路径；不能用内部存储测试证明 CLI 的参数或退出码。

本示例只演示写法。项目的术语、能力、限制与验收结果均须来自该项目的目标和证据；结构与关系检查无法代替这项判断。
