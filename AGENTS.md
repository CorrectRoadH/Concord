# Concord development

Concord is a standalone local SDLC CLI extracted from NiceEval's repository workflows.
Read `docs/architecture.md` for the system structure.
Read `docs/taste.md` before planning, implementing, or reviewing a feature. Concord is spec-driven: the Spec is made of Features (README, Use Cases, architecture, and cli or library examples), and `docs/document-model.md` defines every document group, location and field. The spec is the single source of truth: change the spec first, then implement exactly what it says. Behavior lives in Feature, Use Case, architecture and engineering pages. A Design page holds only an open tradeoff; once decided, write the rule into the spec and delete the page. Link a taste entry next to the sentence that relies on it, and edit `docs/taste.md` directly when a new project-wide preference appears. Git keeps all history; do not add version records, status history, or change logs to docs.
Do not depend on a NiceEval checkout, workspace package, provider credential, deployment service, or global installation.

Keep contracts, executable test definitions, and engineering memories in their own owners. Derive reverse relations; do not store a second registry. Test collection preserves native identities, labels and source bindings; it does not prove execution, coverage or reliability. Coding agents run project tests directly and report the actual scope and results.

Contract prose declares intended behavior, constraints, and acceptance; product workflows belong in contracts. Memory keeps reusable lessons from developing Concord; process logs and delivery progress stay out of the repository. Issues hold only work still to do and are deleted once handled. Edit every file under `docs/` and `memory/` directly; use `concord memory search` and `concord issue search` to search, and do not maintain a manual INDEX. Commands are helpers for steps that must run: read `concord --skill fix` for agent-owned regression testing and `concord --skill feedback` when closing an existing Issue. Closure atomically deletes the Issue and its `@issue` markers and prints the reason for the commit message; it does not run or certify tests. Read `concord --skill memory` for reusable engineering lessons.

Structured terminology and writing policy are owned by directory-scoped `concepts.md` and `writing.md` under docs. Edit them directly and let `concord check` validate structure, scope and references; derive the project glossary and references instead of duplicating definitions in Markdown or a second index. Each concept has one term, with its definition and explanation together in concepts.md. Only deprecated names generate terminology bans.

Follow the [TypeScript code conventions](docs/engineering/code/README.md) for naming, modules and errors; Oxlint enforces static rules. Effect dependencies stay on the exact pinned revision. Read the installed `effect/AGENTS.md` before using its APIs. Use strict Schema decoding at untrusted boundaries and named failures.

Maintain implementation, tests, and build scripts in strict TypeScript with Effect for execution and side effects. Do not add hand-maintained JavaScript scripts or bypass type checking. JavaScript build output and explicit JavaScript-consumer compatibility fixtures are distinct from maintained implementation sources.

Releases are self-contained per-target archives: one `bun build --compile --bytecode` executable, ripgrep, the target's HawDB binding, app resources, and only the external tools the executable loads by package name (TypeScript and esbuild, the sole `dependencies` in `package.json`); users need only Git, and nothing runs pnpm on their machine. Product development, tests, CI and archives use the exact Bun version in `.bun-version`. Development tools also run on Bun. Product code uses APIs supported by the pinned Bun. The release installer `install.sh` is the only maintained shell script: `curl … | sh` needs POSIX sh before Concord exists, so keep it small, checksum-verified and covered by installer protocol tests. The TypeScript packaging entry compiles `bin/concord`, including its internal child-process entries. This repository contains no Rust or HawDB compilation. Concord uses the official `@nowledge/hawdb-bun` adapter and the official HawDB C ABI library releases, with no Rust or N-API fork; Concord pins `native-release.json` and only downloads and validates those binaries. Keep domain decisions, Schema validation, publication authority, tests, and build orchestration in TypeScript/Effect. Pin the binary release version, engine revision and integrity checksums. Each worktree's workspace server, or the current command when none runs, is the single owner of persistent handles; publication never holds them, and a busy persistent cache fails with HawdbBusy without changing execution mode. In-memory cache handles belong to the process. Pack target-native artifacts into each archive so users need no Rust compiler or HawDB service. Engine upgrades must revalidate ownership and clear against the pinned lock protocol.

Use the project-pinned Vite, tsdown and Oxlint tools with Bun. Install with `bun install --frozen-lockfile`; run tasks with `bun run`. Use the pinned Bun package manager and `bun.lock`; overrides, patches and trusted dependencies belong to `package.json`. Run the current source CLI with `bun run concord`; delivery runs tests and static checks separately.

- The checkout never contains `dist/`. Development and tests run TypeScript source with Bun; relative imports use `.ts` extensions and only erasable TypeScript syntax is allowed. The Web bundle and native bindings come from caches outside the checkout keyed by their own inputs, so changing CLI code rebuilds nothing; the release workflow builds each target archive and publishes the same bytes after tests and static checks pass. Build failures propagate directly without a separate archive smoke-test job.
- `bun run test` directly invokes official Bun test. `bun run bench` independently invokes Mitata. Do not add an aggregate gate/check wrapper or a custom test runner.
- Run `bun run typecheck`, `typecheck:test`, `typecheck:scripts`, `typecheck:web`, `lint`, and `bun run concord --json --dry-run check` separately for delivery. CI runs all tests in sixteen official shards.
- 本地只允许运行与当前改动直接相关的单个测试文件（`bun run test <file>` 或 `--test-name-pattern=...`），验证差不多通过即可；严禁在本地执行全量测试以避免单机资源争抢与虚假超时。完整验收与全量回归统一交由 CI 运行。
- `bun run build:native` prepares the pinned official production binaries from validated cache or the official HawDB release; there are no test-hook binaries. Missing or invalid binaries fail without a Cargo fallback. `CONCORD_NATIVE_OFFLINE=1` requires the cache. Release workflows also consume binaries.
- File concurrency uses Bun’s official `--parallel` default; pass `--parallel=N` to choose a worker count. Browser/AI and real Node/Vitest compatibility tests are outside the maintained suite; development and CI do not install Node or Chromium.

The top-level `concord/` folder is the published Herdr mod: generate it with `bun run build:herdr` and commit it with its source changes, without requiring a CLI release. Never edit generated JavaScript by hand. Keep task-result caching disabled for acceptance. Write each test at the lowest layer that observes its result; CLI tests cover argument, output and exit-code mapping, and process tests cover only cross-process guarantees. Tests that modify installed files use copies in their own temp directory. See [build](docs/engineering/build/README.md) and [check entrypoints](docs/engineering/testing/README.md#检查入口) for the maintained workflow. Report failed or skipped checks explicitly.

Develop on master in the main checkout; agents work in parallel there, not in worktrees or branches. Commit small, scoped hunks: stage only your own files or hunks, leave others' uncommitted changes in place, and coordinate through the parent agent only when edits actually overlap. Avoid concurrent heavy tests and benchmark sampling; CI runs on GitHub-hosted `ubuntu-24.04` runners; edit docs and code at any time and re-run results that went stale; re-run timeout or connection-reset failures on an idle machine before attributing them. Follow the shared-resource rules in [testing](docs/engineering/testing/README.md#共享资源与同步): replace possibly mapped files by rename, give destructive tests private installs, use a new HTTP connection per test request, and wait on real product state rather than elapsed time.

Benchmarks are part of the feature: its `performance.md` and `bench/<feature-id>.bench.ts` describe the same operation and measurement boundary. Run affected Mitata files before delivery, or `bun run bench` when shared benchmark code changes. Review native results against applicable budgets; successful sampling alone is not budget acceptance. Do not maintain a custom benchmark CLI, sampler, statistics engine or reporter; see [performance](docs/engineering/performance/README.md#开发与交付流程).

No paid model calls, external mutations, production operations, publishing, or pushing without explicit user authorization.

Workers are not alone in this repository. Preserve other changes, stay within assigned paths, and do not commit unless assigned. Do not use built-in subagents. Herdr delegation follows the user's global guide.
