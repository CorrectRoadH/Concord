# Concord development

Concord is a standalone local SDLC CLI extracted from NiceEval's repository workflows.
Read `docs/architecture.md` for the system structure.
Read `docs/taste.md` before planning, implementing, or reviewing a feature. Concord is spec-driven: the Spec is made of Features (README, Use Cases, architecture, and cli or library examples), and `docs/document-model.md` defines every document group, location and field. The spec is the single source of truth: change the spec first, then implement exactly what it says. Behavior lives in Feature, Use Case, architecture and engineering pages. A Design page holds only an open tradeoff; once decided, write the rule into the spec and delete the page. Link a taste entry next to the sentence that relies on it, and edit `docs/taste.md` directly when a new project-wide preference appears. Git keeps all history; do not add version records, status history, or change logs to docs.
Do not depend on a NiceEval checkout, workspace package, provider credential, deployment service, or global installation.

Keep contracts, executable test definitions, and engineering memories in their own owners. Derive reverse relations; do not store a second registry. A fix verification proves only that one frozen runner command failed on the defect commit and passed on the accepted snapshot; do not claim it proves native test coverage or formal E2E reliability.

Contract prose declares intended behavior, constraints, and acceptance; product workflows belong in contracts. Memory keeps reusable lessons from developing Concord; process logs and delivery progress stay out of the repository. Issues hold only work still to do and are deleted once handled. Edit every file under `docs/` and `memory/` directly; use `concord memory search` and `concord issue search` to search, and do not maintain a manual INDEX. Commands are helpers for steps that must run: close a defect with `concord issue close <id> --fixed` after committing a failing regression test marked `@issue` and then the fix; it verifies, deletes the Issue, and prints the result for the commit message.  Read `concord --skill memory` or `concord --skill feedback` for the current workflow.

Structured terminology and writing policy are owned by directory-scoped `concepts.md` and `writing.md` under docs. Edit them directly and let `concord check` validate structure, scope and references; derive the project glossary and references instead of duplicating definitions in Markdown or a second index. Each concept has one term, with its definition and explanation together in concepts.md. Only deprecated names generate terminology bans.

Effect dependencies stay on the exact pinned revision. Read the installed `effect/AGENTS.md` before using its APIs. Use strict Schema decoding at untrusted boundaries and named failures.

Maintain implementation, tests, and build scripts in strict TypeScript with Effect for execution and side effects. Do not add hand-maintained JavaScript scripts or bypass type checking. JavaScript build output and explicit JavaScript-consumer compatibility fixtures are distinct from maintained implementation sources.

The sole native exception is `native/hawdb`: Rust N-API engine bindings, required linker glue, byte conversion, resource budgets, and the revision-bound HawDB directory ownership guard. Keep domain decisions, Schema validation, publication authority, tests, and build orchestration in TypeScript/Effect. Pin the engine revision, Rust toolchain and bridge dependencies. Each worktree's workspace server, or the current command when none runs, is the single owner of persistent handles; publication never holds them, and a busy persistent cache degrades to the in-memory cache. In-memory cache handles belong to the process. Pack target-native artifacts so consumers need no Rust compiler or HawDB service. Engine upgrades must revalidate ownership and clear against the pinned lock protocol.

Use the project-pinned Vite+ toolchain. Bootstrap with `pnpm install --frozen-lockfile`; use `vp install` thereafter. When no global CLI is installed, prefix Vite+ commands with `pnpm exec`, for example `pnpm exec vp dev`. Keep the pinned pnpm package manager and lockfile. Run the current source CLI with `pnpm concord`; delivery uses `pnpm gate`.

- The checkout never contains `dist/`; development runs source, and the gate builds one package into its own temp directory that the CLI, process and browser tests run. `vp build --outDir <dir>` builds the complete installable package (native bindings, CLI, Web, Preview, packaged resources) into a directory outside the checkout. `vp dev` starts only the Web development server.
- `pnpm gate` (equivalent to `vp run gate`) is the sole check entry: static checks, the package build and the source-level tests run in parallel, then CLI, process and browser tests run the built package. Deliver with `pnpm gate --changed`; CI runs the full set in four shards after each push. Vite+'s built-in `vp check` and `vp test` do not run this project's gate.
- `pnpm gate [files...]` accepts `--changed [<base>]`, `--test-name-pattern=...` and `--test-shard=1/4`. Build and static checks remain complete; say in the delivery which selection ran.
- `vp run build:native` reuses validated shared native artifacts, then downloads the matching digest release, then falls back to Cargo. `CONCORD_NATIVE_OFFLINE=1` skips downloads. Release workflows compile from source.
- Test file concurrency defaults to half the available CPUs (maximum eight); browser workers default to at most four. `CONCORD_TEST_CONCURRENCY` and `CONCORD_E2E_WORKERS` explicitly override these values.

Keep task-result caching disabled for acceptance. Write each test at the lowest layer that observes its result; CLI tests cover argument, output and exit-code mapping, and process tests cover only cross-process guarantees. Tests that modify installed files use copies in their own temp directory. See [build](docs/engineering/build/README.md) and [check entrypoints](docs/engineering/testing/README.md#检查入口) for the maintained workflow. Report failed or skipped checks explicitly.

Develop on master in the main checkout; agents work in parallel there, not in worktrees or branches. Commit small, scoped hunks: stage only your own files or hunks, leave others' uncommitted changes in place, and coordinate through the parent agent only when edits actually overlap. Run at most one full `pnpm gate` per machine at a time, and re-run timeout or connection-reset failures on an idle machine before attributing them. Follow the shared-resource rules in [testing](docs/engineering/testing/README.md#共享资源与同步): replace possibly mapped files by rename, give destructive tests private installs, use a new HTTP connection per test request, and wait on real product state rather than elapsed time.

Benchmarks are part of the feature: a budget row in a Feature's `performance.md` and its scenario in `bench/<feature-id>.bench.ts` change together. Before delivering a change that `vp run bench --changed` selects, run `vp run bench --changed --compare` and keep every verdict passing; see [performance](docs/engineering/performance/README.md#开发与交付流程).

No paid model calls, external mutations, production operations, publishing, or pushing without explicit user authorization.

Workers are not alone in this repository. Preserve other changes, stay within assigned paths, and do not commit unless assigned. Do not use built-in subagents. Herdr delegation follows the user's global guide.
